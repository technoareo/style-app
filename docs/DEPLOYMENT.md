# Single-server launch deployment

Status: implementation and release review in progress. No public service has been provisioned or launched. The local account integration tests pass; this is not evidence of a tested internet deployment.

The chosen initial setup is one self-hosted server: Next.js, Better Auth, SQLite with WAL, a private photo store in the database, one Ollama worker, and Caddy for HTTPS. Software and model inference have no API fee. Hosting, electricity, a domain and mail delivery are separate operator costs; this is not a promise of permanently free public hosting. Ordinary users register, verify email, recover passwords and delete accounts without administrator assistance.

## Server requirements

Use a supported Linux server with Docker Compose, a persistent local disk (not an ephemeral filesystem or network-mounted SQLite file), and sufficient RAM for the 4B vision model. Begin with 16 GB RAM, 4 CPU cores and at least 30 GB free storage, then measure actual capacity. CPU inference is supported but may take minutes. Optional GPU acceleration needs a separately tested configuration. This release is one server, not an automatically scaling deployment.

The domain must point to that server and allow inbound ports 80 and 443. Only the proxy publishes ports. Keep the app, worker and Ollama internal. No model control API is exposed publicly.

## Configuration and first start

Create an untracked `.env.production` containing:

```dotenv
APP_URL=https://your-real-domain.example
STYLE_DOMAIN=your-real-domain.example
AUTH_SECRET=generate-a-unique-random-secret-at-least-32-characters
SMTP_URL=smtps://your-mail-provider-credentials@your-mail-host:465
MAIL_FROM=Style Studio <your-verified-sender@your-real-domain.example>
VISION_MODEL=qwen3-vl:4b-instruct
```

These are examples, not functioning credentials. Generate the secret privately and retain it in your password manager. Configure a real verified mail sender; test verification and recovery delivery to independent email providers. The public application refuses to initialize accounts without an HTTPS origin, an authentication secret and mail configuration. Its public mode is forced on in Compose.

**Vision model (`VISION_MODEL`, build 018).** The model used for photo analysis is read from `VISION_MODEL` in `.env.production`; when it is unset or blank the default `qwen3-vl:4b-instruct` is used. The web app (readiness check), the AI worker (inference) and the readiness answer all read the same setting through one function, so they cannot disagree. The value must be a model reference Ollama can pull: ASCII letters, digits, `.`, `_`, `-`, optional `/` namespace parts and one optional `:tag`, at most 100 characters (for example `qwen3-vl:4b-instruct`, `llava:7b`). A **malformed value is not replaced by the default**: photo analysis then reports unavailable (no request reaches Ollama, the attempt is not charged) and the app logs `[vision] VISION_MODEL is not a valid model name` once, so a typo is visible instead of silently running another model. The model must also be **pulled under exactly that name**: `docker compose exec ollama ollama pull <the same value>`; the readiness check lists Ollama's installed models and reports not ready if the name is absent (an untagged name matches `<name>:latest`). After changing the value, recreate the services that read it with `docker compose up -d` (the `app` and `worker`). The prompt, output schema and token bounds are written for the Qwen3-VL instruct models; another model may ignore the schema, answer slowly or label poorly, and **only the two Qwen3-VL instruct models, the 4B default and the 2B, have been tried, in a handful of development runs on one machine**. See "Single-item photo analysis" below for what has and has not been verified.

**Single-item photo analysis (build 018).** The upload now asks the model for one garment per photo: category, colour, pattern, fit (fitted/regular/relaxed/oversized/not sure), a material only when a texture is plainly visible (denim, knit, leather and similar; fibre such as cotton, wool or silk is never suggested), suggested seasons and occasions (shown beside the fields and applied only when the user presses "Use these" or ticks them), a four-step self-reported confidence (never shown as reassurance; only a low or doubt-capped value produces a note, worded as the AI's own statement, because it is not calibrated: a 2B model answered 1 while unsure of colour, pattern, material and fit, so the server caps the score at 0.5 whenever the model also lists doubts) and a list of attributes the model flagged as unsure. Brand and size are always blank and warmth is never inferred. The request lets the model list up to 3 candidates, most prominent first, so that a second item can be detected at all; the server cuts the answer to the vocabulary, presents and saves exactly ONE item and tells the user when more were listed. **Selection rule (server, documented in `mostProminentIndex`):** the entry with the largest usable box (four numbers inside the frame, right > left, bottom > top) is kept; an unusable box counts as zero; equal areas go to the first listed. The prompt asks the model to list the item that fills most of the picture first, but the server does not rely on the order. Limit: the largest outline can belong to a background garment, which is why a warning is shown whenever more than one was listed. Two shoes are shown as one pair only when the model's own entries are "Left X" and "Right X" with the same colour and pattern, similar size and close together (the user is told to check the crop); a sneaker and a boot, two different pairs, or anything weaker is not merged. Every field is editable at review, "Not sure" / empty is allowed, and the user must tick "Details checked" before saving; seasons, occasions, material and fit are saved on the wardrobe item, the "unsure" flags are not. Crowded or multi-item photos are not supported in this build (the multi-item code path remains in the source but is not used). **Shoes and pairs.** The model may outline one shoe of a pair (a real 4B run named one leather shoe in a photo of a pair and cropped only that one), and nothing in a single answer says which was meant. Every item whose category is Shoes therefore shows a crop check in the review (also after the user changes the category): both shoes should be visible if it is a pair, the name should say so, and "Adjust item crop" is the fix; the item is not presented as verified either way. Automatic pairing from two entries needs the model's own "Left X"/"Right X" entries plus matching colour, similar size and closeness.

**Upgrade with photos still queued (build 018).** Each job records the mode it was accepted under in a new column (`analysis_jobs.analysis_mode`, added by an additive migration). A job queued by an earlier build has no value and runs the multi-item path it was admitted under, with its original result shape; only jobs accepted after the upgrade run the single-item path. No drain is required. Check after upgrading with `SELECT analysis_mode, COUNT(*) FROM analysis_jobs GROUP BY 1` (NULL = queued by the old build). **Rollback switch (build 019).** `STYLE_ANALYSIS_MODE` in `.env.production` chooses the mode NEW jobs are accepted under: unset or blank = `single` (default), `multi` = the earlier up-to-6-item behaviour, kept only as a way back (the review screen can display several items, but its text still asks for one item per photo, and crowded-photo quality is unvalidated: this is a rollback to earlier code, not a supported crowded-photo mode). Only the exact words `single` or `multi` are accepted (case and spaces ignored); any other value makes new uploads fail with 503 and readiness report not ready, rather than guessing. To roll back: set `STYLE_ANALYSIS_MODE=multi`, then `docker compose up -d` (recreates `app`, the process that accepts uploads). Each job stores the mode it was accepted under and the worker obeys the stored value, so changing the switch never alters a photo already queued, in either direction; check with `SELECT analysis_mode, COUNT(*) FROM analysis_jobs GROUP BY 1`. The worker does not need the variable. **Local runs:** the standalone analysis worker loads `.env*` files with Next.js's own loader (`@next/env`, a dependency of `next`): the same file order for its mode, the same `$VAR` expansion, and variables present when the process started win. The worker's mode follows `NODE_ENV` (production only if `NODE_ENV=production`) while `next dev` / `next start` pick theirs from the command, so put settings both processes must share (`VISION_MODEL`) in `.env.local` or `.env`, not in `.env.development` / `.env.production`. `@next/env` is declared as a direct dependency (same version as the one `next` installs). The compiled local launcher (`npm run start`, `scripts/start-server.ts`) runs the standalone `server.js`, which changes directory into `.next/standalone` and so would never see repo-root `.env*` files (read from Next's own server template in `node_modules`, not by running a build here); the launcher therefore loads them itself in production mode before starting the server, and `scripts/start-local.ps1` starts the worker with `NODE_ENV=production` so both read the same files. `npm run dev` plus a worker started without `NODE_ENV` read the development set. Nothing is read when `STYLE_PUBLIC_DEPLOYMENT=true`, so under Compose only `.env.production` applies. **Latency (measured by the owner):** the real installed `qwen3-vl:4b-instruct` took 109.2 s on CPU for one plain photo (it returned one correct white graphic T-shirt); a further run took 132 s on a photo of a handmade leather shoe pair (one perforated leather shoe identified, crop covering one shoe), and the 2B model took 75 s on the shirt; the queue estimate, ETA and `STYLE_INFERENCE_TIMEOUT_MS` must be set from measurements on the target server before users are invited. **Malformed model fields (single-item mode only; multi-item verification is unchanged).** A model that ignores the output grammar is repaired toward "unknown", never toward a guess, and the doubt is recorded: brand and size are always blanked before verification; over-long text is cut to its cap; a missing or non-text colour or pattern becomes empty and is flagged; a category outside the list becomes Unsorted (the review will not save it until the user chooses) and is flagged; a formality outside the list becomes unknown; a confidence that is not a number from 0 to 1 becomes 0.25 ("poor guess"); an item with no name is shown with an empty name field that must be filled before saving, so no label is invented. An entry that is not an item at all (null, text, a number) is **not** repaired: verification fails, the user sees the generic retry message, and because the model ran this is recorded as a model failure and **charged, not refunded** (refunds are only for server-side failures: model unreachable, timeout, worker lost, expiry). A repaired item is a normal completed analysis and is charged once. This is covered by tests that run the real queue against a mock model; real models may fail in other ways not seen yet. **Warnings.** Only demonstrably non-actionable model warning text is removed before the user sees it: an empty placeholder (`none`, `n/a`, `ok`), a sentence of at least 20 characters copied word for word from our own instructions, and one observed echo ("Only count physical garments. Ignore prints, drawings, text, or people."). Any other warning is shown exactly as written, so an unfamiliar phrasing of the same boilerplate can still appear. **Capacity, candidly.** Observed single runs on this CPU: 75 s (2B), 102 s, 109 s, 114 s and 132 s (4B), one photo at a time through one worker. That is roughly 27 to 48 photos an hour at best, for one worker, if nothing else uses the machine; crowded photos took 255 s and more in an earlier build. Against the defaults: the per-job estimate (`STYLE_ANALYSIS_ESTIMATE_MS`, 120 s) sits inside the observed range but under the slowest run, and recent measured durations raise it after the first jobs; the admission check assumes the worst case, `max(estimate, inference timeout + 10 s)` = 250 s per job ahead, about twice what was observed, so with a 10-minute review budget it admits at most 11 queued photos site-wide while real throughput would allow about 20 or more waiting inside the one-hour lifetime. That conservatism protects users from expiry and wastes capacity; lowering `STYLE_INFERENCE_TIMEOUT_MS` would raise admission but would fail any photo slower than the new limit, so change it only from your own p95/p99 measurements. No response-time guarantee is offered or implied: a user can wait many minutes, and the numbers above are single runs, not a load test. **What has and has not been verified:** the only real-model evidence is a handful of development runs recorded in `docs/verification/REAL_VISION_018_ROOT.md` (the 4B on a shirt, a hoodie and a CC0 shoe photo; the 2B on the shirt; and, after the schema repair, the 4B on the shirt again in 102.2 s). They show that the schema is accepted and what went wrong (slow, one shoe of a pair cropped, uncalibrated self-scores, boilerplate warnings); they are samples from three photos, **not a representative benchmark**, and say nothing reliable about accuracy. Recognition quality across photos, the season/occasion suggestions and the confidence scores remain unmeasured, and a set of evaluation photos whose owners consented is required before any accuracy claim. **Crowded and multi-item photos are not validated at all in this build**: the single-item path is the supported goal, and the `multi` rollback restores earlier code, not a reliable crowded-photo feature (the only crowded photo ever tried, in an earlier build, produced six poorly labelled items in 255 s). The automated tests use generated images, not copyrighted photographs.

**Proxy domain file (build 015 revision 2; the commands have not been run in Docker).** The `proxy` service no longer loads `.env.production`; it receives only two non-secret values (`STYLE_DOMAIN` and, since build 017, `STYLE_BODY_READ_TIMEOUT_MS`, below), so the public-facing container never holds `AUTH_SECRET` or the SMTP credentials. Docker Compose substitutes `${STYLE_DOMAIN}` in `compose.yaml` from the shell, from a `.env` file next to `compose.yaml`, or from `--env-file`; it does **not** take it from a service's `env_file`. So, once, in the directory that contains `compose.yaml` and BEFORE the commands below, create the domain-only Compose file from the template:

```sh
# Creates .env only if it does not exist yet. Never overwrites an existing .env.
[ -e .env ] || cp .env.compose.example .env
# Then edit .env so its single line reads STYLE_DOMAIN=<your real domain>,
# the same domain as STYLE_DOMAIN and APP_URL in .env.production.
```

`.env.compose.example` holds one non-secret variable (`STYLE_DOMAIN`, with a public placeholder value). Keep every secret in `.env.production`, never in `.env`. If a `.env` already exists on that machine for another purpose, do not overwrite it: use the `--env-file` alternative below. Compose reads `.env` in every shell and every version, so the later commands (including the restore procedure's `docker compose up -d` in a fresh shell) keep the same proxy domain.

```sh
docker compose build
docker compose up -d ollama
docker compose exec ollama ollama pull qwen3-vl:4b-instruct   # or the exact VISION_MODEL value you set
docker compose up -d
```

**Alternative without `.env`:** put the flag on every compose command that can create or recreate the proxy, for example `docker compose --env-file .env.production up -d`. A command run without it (a new shell, the restore step) sees a different proxy configuration, recreates the proxy with an empty domain and, because of the guard below, leaves it restarting until you fix that. Prefer the `.env` file for that reason. `COMPOSE_ENV_FILES` (an environment variable that points Compose at env files) can do the same for one shell, but it lasts only as long as that shell, and the Compose version that first supports it is **not established** here; do not rely on it.

**Startup guard.** The proxy command first checks that `STYLE_DOMAIN` is non-empty and otherwise prints `STYLE_DOMAIN is not set` to its log and exits with code 1 before `caddy` starts, then runs the standard `caddy run --config /etc/caddy/Caddyfile --adapter caddyfile`. With `restart: unless-stopped` a missing value shows as a restarting proxy in `docker compose ps` and as that message in `docker compose logs proxy`. The guard has been written but **never run**. The `:-` default in `compose.yaml` is deliberate: with `:?` every compose command, including the documented `exec` and `run` recovery commands, would fail when the variable is missing. After the first start, check `docker compose exec proxy printenv STYLE_DOMAIN` (prints only the domain), `docker compose logs proxy`, and that the proxy answers on your domain before announcing the service. The guard checks that the value is non-empty, not that it is correct. `tests/proxyConfig.test.ts` reads `compose.yaml` and this guide as text and cannot show that Docker substitutes or Caddy starts.

Compose starts the app schema before serving requests. The worker and proxy wait for the app's authenticated-database health check. A shared, heartbeating filesystem lock serializes schema migrations across processes; three simultaneous cold-start processes have passed a local test. The worker and app share only their persistent account volume. The actual container cold start remains untested here because Docker is unavailable. An accidentally started second worker is prevented from claiming work by the database ownership lock.

## Release checks before inviting users

Create two real accounts using the public sign-up form. Verify their emails. Upload clothing, review the crops, save an outfit, then sign in from another browser and confirm the same private wardrobe appears. Attempt to access the other account's photo URL and confirm it is denied. Reset a password and confirm previous sessions stop working. Delete an account and confirm its active wardrobe and photos are removed. No administrator should be needed for these user flows.

Test concurrent uploads, cancellation, worker downtime and restart, and daily account limits. Verify HTTPS, secure cookies, proxy headers and unauthenticated responses on the actual domain. Measure queue time and inference time with the intended server. Run the automated checks and obtain Claude's independent review of the exact built source and evidence. Passing local tests does not replace these release checks.

## Runtime limits (build 007)

All are optional environment variables in `.env.production`; invalid or out-of-range values are ignored and the default is used. Defaults are conservative starting values, not measured capacity. The target-server load test must confirm or replace them, and Docker has not been run here, so `mem_limit` and `NODE_OPTIONS` in `compose.yaml` are untested starting points.

| Variable | Default | Meaning |
|---|---|---|
| `STYLE_MAX_UPLOAD_BYTES` | 2500000 | Largest decoded photo accepted (the app's own client sends a 1600 px JPEG, usually under 1 MB) |
| `STYLE_MAX_UPLOAD_SIDE` | 2400 | Longest side allowed, read from the file header before decoding |
| `STYLE_MAX_UPLOAD_PIXELS` | 6000000 | Raster size allowed, read from the header before decoding |
| `STYLE_BODY_READ_TIMEOUT_MS` | 20000 | A stalled upload is dropped after this. **Under Compose set it in the project `.env`, not here** (build 017, see "Proxy transport behaviour"); the table's "invalid values are ignored" rule does not apply there, an invalid value stops the containers |
| `STYLE_IMAGE_CONCURRENCY` | 2 | Process-wide photo reads/decodes at once (photo and analysis routes share it) |
| `STYLE_IMAGE_QUEUE` | 6 | Callers allowed to wait for a slot; more are refused with 503 and `Retry-After` |
| `STYLE_IMAGE_WAIT_MS` | 15000 | Longest wait for a slot |
| `STYLE_QUEUE_MAX_ACTIVE` | 20 | Queued + running analyses across all accounts |
| `STYLE_ANALYSIS_MODE` | single | Mode for NEW jobs: `single` or `multi` (rollback). Anything else refuses new uploads (503) instead of being ignored. Queued jobs keep their stored mode. See "Rollback switch" |
| `STYLE_ANALYSIS_ESTIMATE_MS` | 120000 | Work time per photo for the displayed ETA, and a floor for admission (which also assumes at least the full inference timeout + 10 s). Measured recent durations (+25%, capped at the timeout) can only raise it |
| `STYLE_REVIEW_BUDGET_MS` | 600000 | A photo is refused unless its estimated ready time plus this review time fits inside its one-hour lifetime |
| `STYLE_INFERENCE_TIMEOUT_MS` | 240000 | Model request timeout |
| `STYLE_JOB_WATCH_MS` | 1000 | How often the worker checks a running job for cancel, account deletion or expiry |
| `STYLE_DAILY_ANALYSES` | 20 | Chargeable analyses per account per UTC day (refunds restore these) |
| `STYLE_DAILY_ATTEMPTS` | 40 | Accepted attempts per account per UTC day; never refunded, bounds refund abuse |

Set `STYLE_ANALYSIS_ESTIMATE_MS` from the measured p95 inference time on the target server. Admission is guaranteed against the worst case, not the estimate: each job ahead is assumed to take the full inference timeout plus 10 s (`max(estimate, STYLE_INFERENCE_TIMEOUT_MS + 10 s)`), while the ETA shown to users uses the estimate. With the defaults that is 250 s per job ahead and a 10-minute review budget, so a new photo is refused once 12 jobs are ahead of it (11 are admitted), well under the global cap of 20. The job lease is `max(10 min, inference timeout + 2 min)`. A job re-run after a worker crash waits for its lease and is not covered by the guarantee; if it then misses the hour it is expired and refunded.

## Backups and operations

Use `docker compose exec app ./node_modules/.bin/tsx scripts/backup-database.ts` for a consistent SQLite backup. Do not copy only the live `app.db` while WAL writes are in progress. The backup includes private account and photo data. **Plain backups from this command are not encrypted, and the software does not copy any backup off the server.** For a portable encrypted copy use `scripts/backup-encrypted.ts` (see "Encrypted backup packages (build 021)" below); copying it off the server is still the operator's responsibility and nothing in this repository does or has exercised it. Protect the authentication secret separately, and perform a restore drill on an isolated server before launch.

Account deletion removes live records immediately (including queued account mail, by cascade) and records a pseudonymous deletion ID (internal user ID and time) for safe restoration. This is a logical delete, not a secure wipe: bytes can remain in unused database pages and in the write-ahead log until overwritten (secure-delete, WAL truncation and physical marker tests are future required work). The backup command retains local copies for seven days in `/data/backups` on the same volume as the live database, and strips temporary AI photos, queued account mail, reset tokens and session tokens from each copy; it still contains every saved account and photo as of its time. Apply the same seven-day limit to any off-server copies you make. Restoring onto a fresh server without the live database is supported since build 010, with a current deletion ledger (see "Deletion ledger and disaster recovery" and "Encrypted backup packages" below); without one the restore command refuses. Operator backups remain private and must never be exposed by the web server.

**How a backup is made (build 009).** One backup runs at a time per backups directory (the lock is an operating-system file lock held by the backup process on `backups/.backup-coordinator.db`, an empty database file that is never written to and is separate from the live database and its write gate; every process and container on the same local volume shares it; a second backup waits up to 30 s, then stops with a clear message). There is no lease, timestamp or "stale" rule: the operating system grants the lock to one process and releases it the instant that process ends, however it ends. So a backup busy in a long blocking step (VACUUM on a big database) keeps the lock however long it takes, and a backup that was killed or crashed frees it immediately, after which the next backup removes the dead process's partial. A backup that hangs forever (or a frozen process) keeps the lock until you kill it; others then time out with the clear message. **Keep `/data` on a local volume** (a Docker named volume or local disk): file locks on NFS/SMB are not reliable, and publication is also no-overwrite so a broken lock still cannot replace a completed backup. The empty `.backup-coordinator.db` stays in the backups directory between runs; do not copy it off the server. An old `.backup.lock` directory from the first 009 build is unused and can be deleted. The raw copy is first written to `style-<time>.<hex>.partial`, sanitised, vacuumed, integrity-checked, and only then renamed to a final `style-<time>.db` name that did not already exist; an existing backup is never replaced, and two backups in the same millisecond get `-1`, `-2` suffixes. **While a backup runs, and after a crash or kill, the `.partial` file exists and is not sanitised**: it holds temporary photos, queued mail, reset tokens and session tokens, unencrypted, in the private (0700) backups directory. It is never a restore source and never matches the retention rule. **Copy only `style-*.db` files off the server, never `*.partial*` or `.backup.lock`.** A failed backup deletes its own partial; the next backup deletes any partial a dead process left (it can do so safely because it holds the lock). If a partial cannot be deleted (permissions, a locked file) the backup command says so on stderr and exits with code 2 (or 1 for a failed backup); delete the named file by hand. Exit codes: 0 done, 1 failed with nothing published, 2 leftover file needs removing.

To restore, stop the app, proxy, worker and mailer, retain the latest live database containing deletion records, and run the restore command against a filename in the private backups directory. The command verifies database integrity, reapplies newer deletion records, removes temporary AI data and **all queued account mail (nothing stale is ever replayed)**, invalidates sessions and old mail tokens, **invalidates every sign-in password**, and only then replaces the stopped database. An isolated local drill has passed; repeat it on the target server before release.

**After every restore, every user must set a new password.** A backup holds the password hashes of its day; a password reset after the backup (a leaked password, say) would otherwise come back with it. The backup cannot say who changed a password, so all credential passwords are emptied in the restore transaction. Users choose a new one with "Forgot password" (the existing email link); **this needs working SMTP and a running `mailer`, so confirm both before telling users the service is back, and tell them to expect to use "Forgot password"**. Accounts, wardrobes and photos are kept. No password or secret is generated or printed. A restored user who tries to delete their account must reset their password first. Restoring onto a fresh server is supported with a current deletion ledger (see below).

> **Build 010 supersedes two statements above.** Restoring onto a fresh server IS now supported, but only with a current deletion ledger (see "Deletion ledger and disaster recovery" below). Backups no longer fail silently on I/O errors: exit code 2 also covers a directory flush that hit a real I/O error (`BACKUP_W_DIR_SYNC_FAILED`) and a published backup whose partial name could not be removed.

### Main database connection unusable (build 016)

After a failed write whose rollback also fails, the app quarantines its main database connection and logs one line: `[database] main connection quarantined: outcome=<replaceable|unclosed|marked-only> count=<n>` (fixed text only; no SQL, path or user data).

- **`outcome=replaceable`**: the quarantined handle was closed and is eligible for reopen. This is **not** proof that a fresh connection is already in use: the next database call opens one, and if that fails (disk full, I/O errors) writes keep failing and `/api/health` still answers 200. Investigate if the count repeats.
- **`outcome=unclosed`**: the handle could not be closed. This process refuses every main-database access until it is restarted (wardrobe and photo writes fail), the stuck transaction may hold SQLite's write lock against the worker and mailer, and `/api/health` returns 503 `{"ready":false}`. The state is never cleared, even if the handle later closes; only a restart clears it.
- **`outcome=marked-only`**: the quarantined handle was not the current shared connection. It was marked quarantined, but **this call only marks it and does not close it**. The line says nothing about whether that handle was closed earlier, whether the shared connection was replaced, or whether the current connection is healthy. Treat a repeating count like `replaceable`: investigate.

**Plain Compose does not recover this.** `restart: unless-stopped` acts only when the process exits, so an unhealthy `app` is flagged but not restarted, and the current Caddy config has a plain `reverse_proxy` with no active health check, so it does not route around the 503. Alert on `app` unhealthy and on the log line above.

Action for `unclosed` (or a repeating `replaceable`):
1. Where practical drain first (let in-flight uploads and analyses finish); a restart cuts any request still running.
2. Restart the `app` service (`docker compose restart app`).
3. Inspect the `worker` and `mailer` logs for repeated busy or timeout errors; restart them if they are stuck. They have **no** equivalent unusable signal: the `worker` has no Compose health check at all, and the `mailer` health check (a heartbeat row) may stay green while its writes are blocked.
4. Confirm `/api/health` returns 200 and a test sign-in and wardrobe write work.
5. **Never** delete, move or copy the live `app.db`, `app.db-wal` or `app.db-shm` by hand.
6. Afterwards take a verified backup, record the incident (time, count, log lines) and, if it recurs, check the data volume is a local disk or Docker volume, not NFS/SMB.

Automatic recovery (an autoheal on the unhealthy status, or workers exiting after the current job) is not implemented and is an open owner decision.

## Account mail (build 008)

Verification and password-reset messages go through a durable outbox table (`mail_outbox`) and are sent by the separate `mailer` service (`scripts/mail-worker.ts`), supervised by Compose (`restart: unless-stopped`, health check via a heartbeat row). Web requests only insert a row; SMTP is never contacted by the web process or by the AI worker. Delivery is **at-least-once** (a crash after SMTP accepts a message but before the outcome is recorded sends it again; both copies share one Message-ID), not exactly-once.

| Bound | Default | Environment variable |
|---|---|---|
| Delivery window (message expires, body cleared) | 45 min | `STYLE_MAIL_WINDOW_MS` |
| SMTP attempts per message | 5 | `STYLE_MAIL_MAX_ATTEMPTS` |
| Backoff | 30 s × 4ⁿ⁻¹, capped at 20 min, +≤10 % jitter | `STYLE_MAIL_BACKOFF_MS`, `STYLE_MAIL_BACKOFF_CAP_MS` |
| Whole-send timeout | 45 s | `STYLE_MAIL_SEND_TIMEOUT_MS` |
| Per address and kind per hour | 4 | `STYLE_MAIL_PER_RECIPIENT_HOUR` |
| Per address per day (all kinds) | 12 | `STYLE_MAIL_PER_RECIPIENT_DAY` |
| Waiting plus sending, service-wide | 1000 | `STYLE_MAIL_MAX_PENDING` |
| Accepted per hour, service-wide | 600 | `STYLE_MAIL_MAX_PER_HOUR` |
| Metadata kept after delivery/expiry/failure | 24 h (no address, no body) | fixed |

**Worker health and shutdown (build 009).** The worker reports in from its own timer every `STYLE_MAIL_HEARTBEAT_MS` (10 s), whatever it is doing, but only while its loop keeps making progress; a process whose event loop is stalled, or a loop wedged for longer than one bounded step (send timeout + 3 s, or the 10 s claim budget, plus a 15 s margin), stops reporting. `--check` and the Compose health check call it healthy while the last report is younger than `STYLE_MAIL_HEALTH_FRESH_MS` (60 s, never below three beats). A long run of slow but progressing deliveries therefore no longer looks unhealthy. On SIGTERM (or SIGINT) the worker stops claiming, cancels the send in flight by destroying its SMTP socket, puts that message back in the queue (its attempt is not counted) with a short record budget (3 tries of 2 s), and exits; the worst legitimate case is about 16.5 s, anything still running after `STYLE_MAIL_SHUTDOWN_EXIT_MS` (25 s) is abandoned (exit code 1) and the row returns to the queue when its lease lapses, which can send it twice (at-least-once, as before). Compose gives the `mailer` service `stop_grace_period: 40s` and runs it as `node --import tsx` so node receives SIGTERM directly. Compose still does not restart a container only because its health check fails: alert on `unhealthy`. Not run in Docker yet.

## Deletion ledger and disaster recovery (build 010)

**Why a separate ledger.** A restore must delete again every account that was deleted after the backup, or that person's wardrobe and photos come back. The live database knows (its `account_deletions` table). A new server does not, and a ledger saved only at backup time cannot know about later deletions. So the ledger is a separate, continuously maintained file, `/data/ledger/deletion-ledger.json`: internal user ids and deletion times only, a few bytes per deleted account, append-only, with a format version, a generation counter, an export time and a SHA-256 checksum.

**How it is kept current.**
- the `mailer` rewrites it about once a minute when the database has a deletion the file lacks (and at least every 15 minutes, so its export time stays recent);
- every `scripts/backup-database.ts` run rewrites it after the backup (so its export time is later than the backup);
- `docker compose exec app ./node_modules/.bin/tsx scripts/export-deletion-ledger.ts` writes it on demand. Run this from cron immediately before you copy the file off the server.

**What the software does NOT do.** It does not copy the ledger anywhere. The file is on the same volume as the database, so it only protects you after a total loss of the volume if **you copy it off the server, separately from the backups and much more often** (every few minutes is cheap; the file is tiny). The age of the last off-server copy is the recovery point for deletions: accounts deleted after it was copied come back on a restore from a fresh server, and the restore tells you the ledger's export time so you can delete them again. Keep the copy where only the operator can write; the checksum detects truncation and accidental edits, it is not a signature.

**Choosing the ledger for a disaster recovery.** Use the newest copy you have. The restore refuses a ledger that is damaged or not a ledger, that was exported before the backup was made, or that is older than `STYLE_RESTORE_LEDGER_MAX_AGE_HOURS` (default 24) unless you set `STYLE_RESTORE_ACCEPT_STALE_LEDGER=true` knowing which deletions you may lose. A restore with no live database and no ledger is refused outright.

**Process coordination.** Every application process that opens the live database (app, AI worker, mailer, the backup and ledger commands) holds a shared lock on `/data/.process-presence.db` while it does. The restore takes an exclusive claim on that file first, so an idle running service makes it refuse (`RESTORE_E_ACTIVE`) before anything changes; a crashed or killed process never blocks it (the operating system releases the lock). A starting service waits at most a few seconds while a restore runs and then fails; the supervisor restarts it. This covers this application's own processes only: stop everything, including any shell or script of your own that opens `app.db`. It assumes a local volume, like the backup lock.

### Restore procedure

Restore into the **same** server (live database present) or a **fresh** one (empty data volume). In both cases:

1. Stop everything that uses the volume: `docker compose stop proxy worker mailer app`.
2. Fresh server only: put the backup file in `/data/backups/` and the newest off-server ledger copy somewhere readable; the server needs the same `.env.production` (including `AUTH_SECRET`).
3. Run the restore (the exit code is 0 done, 1 refused or failed with the existing database unchanged, 2 restored with a warning):

```sh
# same server, live database present (uses its account_deletions, plus /data/ledger when valid)
docker compose run --rm -e STYLE_RESTORE_CONFIRMED=true app ./node_modules/.bin/tsx scripts/restore-database.ts style-YOUR-BACKUP-TIMESTAMP.db

# fresh server: the ledger is REQUIRED
docker compose run --rm -v /path/to/ledger-dir:/ledger:ro -e STYLE_RESTORE_CONFIRMED=true app ./node_modules/.bin/tsx scripts/restore-database.ts style-YOUR-BACKUP-TIMESTAMP.db --ledger /ledger/deletion-ledger.json
```

4. `docker compose up -d`. Before announcing the service: confirm SMTP works (the `mailer` is healthy and `--status` shows no growing `failed` count), and tell users to choose a new password with "Forgot password".

If a live database is present and a `/data/ledger/deletion-ledger.json` exists but is damaged, the restore stops (`RESTORE_E_LEDGER_INVALID`); pass `--ledger` with a good copy, or move the damaged file away. If the live database cannot be opened (`RESTORE_E_LIVE_UNREADABLE`), move `app.db` aside deliberately and restore as a fresh server. Diagnostics are fixed codes (`RESTORE_E_*`, `RESTORE_W_*`) without paths or ids.

The restore builds its replacement in a unique owner-only staging file (`app.db.restore-<hex>.pending`) in `/data`, verifies it completely (integrity, the application's tables, relationships), and only then replaces `app.db`. Any failure removes the staging file; a crash leaves it, and the next restore removes leftovers of that exact name pattern. Not run in Docker yet; local drills on Windows only.

**Backups and client addresses.** Completed backups and restores also empty Better Auth's rate-limit table, whose keys contain client IP addresses.

## Encrypted backup packages (build 021)

`scripts/backup-encrypted.ts` makes **one encrypted, portable file** that holds the sanitised database backup and the deletion ledger exported at or after it. `scripts/restore-encrypted.ts` restores from it, including onto a **fresh, empty data volume**. It uses Node's built-in crypto only: AES-256-GCM with a fresh random salt and nonce per package and a key derived from your passphrase with scrypt (N 2^17, r 8, p 1 by default, about 128 MiB of memory while deriving; the container needs that free). The 64-byte header (format version, scrypt settings, salt, nonce, backup time, lengths) is authenticated, and the file size must match it exactly.

**What it protects, and what it does not.** It protects the copied artifact **at rest**: a package that is copied off the server, left in a bucket or read from a stolen disk image is unreadable and tamper-evident without the passphrase. It does not protect against anyone who has the passphrase, against a compromised running server (the live database and the app secret are on it), or against loss of the passphrase: **if the passphrase is lost the data cannot be recovered, by anyone, including you.** It is not a signature scheme; the passphrase makes and opens packages.

**Passphrase.** Never an argument (arguments are visible to every local user and land in shell history). Provide exactly one of `STYLE_BACKUP_PASSPHRASE_FILE` (a path to a protected file; preferred) or `STYLE_BACKUP_PASSPHRASE`. A file must be a plain file of at most 4 KiB; on Linux it must be owned by the user running the command (uid 1001 in the container) with mode 0600 or 0400, and a link or a group/world-readable file is refused. At least 20 characters with at least 10 different ones is required, else the command refuses before doing anything (`openssl rand -base64 32` makes a good one). The software never prints or stores it. Keep it **somewhere other than this server and apart from the packages** (a password manager or secret store the on-call people can reach), and write down which passphrase belongs to which packages: a later change of passphrase does not re-encrypt existing packages.

```sh
# create (the passphrase file is mounted read-only; chown 1001 and chmod 600 it first)
docker compose run --rm -v /secure/backup-passphrase.txt:/run/secrets/backup_passphrase:ro -e STYLE_BACKUP_PASSPHRASE_FILE=/run/secrets/backup_passphrase app ./node_modules/.bin/tsx scripts/backup-encrypted.ts
```

`backup-encrypted.ts` takes the ordinary sanitised backup, exports the ledger after it, writes the package to a partial file, **re-opens the partial exactly as a restore would** (full authentication), and only then publishes it. It also takes `--keep-local`. The ordinary plain backup made by that run is removed **after** publication (never before); with `--keep-local` it stays. Exit codes: 0 done; 1 failed, nothing published; 2 published, but a named leftover file, a failed directory flush or an unremoved plain backup needs you.

**Where it goes and how it is published.** `/data/exports` (a private directory, 0700 on Linux, created by the command; a link or junction in its place is refused) on the **same volume as the database**. Names are `style-package-<UTC time>[-n].stylepkg`. The file is created exclusively with owner-only permissions under a fixed `.partial` name, flushed, verified and then **hard-linked** to its final name, which fails rather than replace an existing file (a duplicate name or a link in the way gets the next free number); the partial name is removed after. A failure, kill, wrong passphrase at verification, a truncated or damaged write, or a stage error publishes nothing and never touches the live database or an earlier package. One export runs at a time (an operating-system file lock); under it only leftover files named exactly `style-package-<time>.<12 hex>.partial` are removed, and anything else in the directory is left alone and, if it looks like a stuck partial, reported. Copy **only** `*.stylepkg` off the server, never a `.partial` or `.export-coordinator.db`. **Packages are not pruned**: each is about the size of the database, so apply your own retention (use the same seven-day limit as plain backups) both here and off the server.

**Restore (including a fresh server).** Stop everything that uses the volume, put the package in `/data/exports/` (create the directory on a new volume; the server needs the same `.env.production`, including `AUTH_SECRET`), then:

```sh
docker compose run --rm -v /secure/backup-passphrase.txt:/run/secrets/backup_passphrase:ro -e STYLE_BACKUP_PASSPHRASE_FILE=/run/secrets/backup_passphrase -e STYLE_RESTORE_CONFIRMED=true app ./node_modules/.bin/tsx scripts/restore-encrypted.ts style-package-YOUR-TIME.stylepkg
# optionally add a NEWER ledger copied from the old server (merged with the packaged one):
#   ... scripts/restore-encrypted.ts style-package-YOUR-TIME.stylepkg --ledger /ledger/deletion-ledger.json
```

The restore uses the same shared code as `restore-database.ts` (live and fresh modes, the exclusive process-presence claim, the integrity and foreign-key checks, every password invalidated, sessions, reset tokens, queued mail, temporary analysis data and rate-limit rows emptied, the replacement as the very last step). In addition it: looks the package up by exact name in `/data/exports` only (a path, a link or a directory is refused); checks magic, version, scrypt settings, declared sizes and the real file size **before** deriving the key; authenticates the **whole** file before writing anything (a wrong passphrase, a changed byte or a truncation is refused with `RESTORE_E_PKG_AUTH` or `RESTORE_E_PKG_TRUNCATED` having changed nothing); decrypts only then, to an owner-only file in `/data/restore-staging`; and removes that file whether the restore succeeds, is refused or fails (a leftover that cannot be removed is named with `RESTORE_W_STAGING_LEFT` and exits 2). Removal is an unlink, not a wipe: run restores on an encrypted volume if deleted plaintext on disk matters to you.

**Ledger freshness still applies.** The ledger inside a package is as old as the package. A fresh-server restore refuses it once it is older than `STYLE_RESTORE_LEDGER_MAX_AGE_HOURS` (default 24) unless you set `STYLE_RESTORE_ACCEPT_STALE_LEDGER=true`; accounts deleted after that ledger's export time come back and the restore prints the time so you can delete them again. Keep copying `/data/ledger/deletion-ledger.json` off the server often and pass the newest copy with `--ledger`; it is merged with the packaged one. On a server that still has its live database, the live deletion records are used as well.

**Operator checklist.** Nothing in this repository copies a package off the server. Until you have configured that copy **and restored from the off-server copy on a different machine**, you do not have an off-server backup: (1) copy packages and the ledger off the server on a schedule; (2) keep the passphrase elsewhere; (3) rehearse a restore on an isolated server before launch and after any change of passphrase; (4) accept that a lost passphrase means unrecoverable data. Still **unverified**: copying a package off the server, restoring on a different machine, the compose file and proxy, and your own operator procedure. Local tests ran on Windows only, where owner-only file modes do not apply.

**Upload bounds (builds 012-013).** Every request body is read under an absolute 20 s deadline (`STYLE_BODY_READ_TIMEOUT_MS`, 1 s to 120 s) that progress does not extend, and a size cap: 32 KiB for account requests, 3,000,000 bytes for `PUT /api/wardrobe`, and the photo limit for `/api/photos` and `/api/analyze`. Operators read it from inside the container, for example `docker compose exec app node -e "fetch('http://127.0.0.1:3000/api/health/uploads').then(r=>r.text()).then(console.log)"`, and should keep it off the public proxy; removing the `@upload_counters` block publishes the totals, which show when image slots are saturated. The block is covered by a static text test only (`tests/proxyConfig.test.ts`); Caddy and Docker have not been run. These counters reset when the process restarts and are per process.

### Proxy transport behaviour (build 016; AUTHORED, NOT RUN)

`deploy/Caddyfile` now sets, for every listener (80 and 443):

| Setting | Value | Effect |
|---|---|---|
| `protocols` | `h1` | HTTP/1.1 only. No HTTP/2, no HTTP/3. |
| `read_header` | 10 s | A client that has not finished sending request headers is dropped. |
| `read_body` | app body deadline + 2 s, derived at start (default 22 s) | **Hard limit on the whole request body**, not an idle timer. |
| `read_body_idle` | same value as `read_body` (build 017 revision 3) | Stall timer on the body. Caddy's default is 1 m, which is shorter than app deadlines of 60 s or more; see "60 s probe failure" below. |
| `idle` | Caddy default (5 m) | Unchanged. |
| `write`, `write_idle` | unset / default | Unchanged on purpose: nothing cuts a long answer or photo download. |
| `reverse_proxy` | any upstream `4xx`/`5xx` is copied unchanged with `Connection: close` added | The client connection closes after an error answer. |

Unchanged: `request_body max_size 10MB`, the security headers, the `404` for `/api/health/uploads` and below, and a single `reverse_proxy app:3000`.

**Why.** Measured earlier on HTTP/1.1 with the previous rules (`docs/verification/TRANSPORT_FINDINGS_014.md`): the app answered a stalled upload with 408 after about 20 s, but through Caddy the client received nothing for more than 35 s, so a stalled or trickling upload could hold a connection open. A local candidate with a 22 s body limit, a 10 s header limit and the close-on-error rule returned the original 408 at about 20 s and closed the socket before the client gave up; normal browser flows (37 passed, 1 skipped) and keep-alive for successful health requests also held. That was a loopback run with a different Caddyfile (no TLS, local paths). This file has not been run.

**Why HTTP/1.1 only.** The same candidate over HTTP/2 was not resolved: after the 408 the connection ended with a GOAWAY. Until a stalled-upload probe passes over HTTP/2 on the target, `protocols h1` is the conservative choice. The cost: no HTTP/2 multiplexing (browsers open several parallel connections instead; the photo upload and wardrobe flows are few, small requests), and no HTTP/3 (compose publishes TCP 443 only, so it was never reachable). Remove the line only after that probe.

**Body limit: one setting for app and proxy (build 017; AUTHORED, NOT RUN in Docker).** `read_body` must stay above the app's body deadline or the proxy cuts the upload first and the client gets a dropped connection instead of the app's 408 message. Build 016 asked the operator to set two variables; forgetting the second silently capped real uploads. Now there is **one** non-secret Compose project variable, `STYLE_BODY_READ_TIMEOUT_MS`, whole milliseconds from 1000 to 120000, default 20000:

- `compose.yaml` hands it to the `app` and `proxy` services under the container name `STYLE_COMPOSE_BODY_READ_TIMEOUT_MS`, with the same expression `${STYLE_BODY_READ_TIMEOUT_MS:-20000}` for both. The app's start command validates it and then exports it as `STYLE_BODY_READ_TIMEOUT_MS`, the name the application reads. (The different name is deliberate: it lets the app see a leftover `STYLE_BODY_READ_TIMEOUT_MS` from `.env.production`, see Migration.)
- The proxy start command derives the Caddy cap as `ceil(ms / 1000) + 2` seconds (20000 gives 22, 60000 gives 62, 120000 gives 122) and exports it as `STYLE_PROXY_BODY_READ_TIMEOUT_S`, which `deploy/Caddyfile` reads. There is no separate proxy setting.
- To change it, put the line in the project `.env` next to `compose.yaml` (the template has it commented out) and run `docker compose up -d`, which recreates the `app` and `proxy` containers. Do **not** put it in `.env.production`.
- **Strict check, in the `app` and `proxy` start commands (identical text):** 4 to 6 digits only, no leading zero, at most 120000. Anything else (empty, `0999`, `20000s`, `1e4`, `0x4e20`, spaces, a sign, a decimal point, `120001`, a very long number) makes the container print `STYLE_BODY_READ_TIMEOUT_MS must be whole milliseconds from 1000 to 120000 with no leading zero` and exit 1, so `docker compose ps` shows it restarting and the proxy never starts with a guessed cap. This is deliberately stricter than the application, which silently falls back to 20000 for an invalid value (`src/server/limits.ts`, unchanged); that fallback would otherwise differ from the derived proxy cap.
- **Migration (fails closed).** If `.env.production` from an earlier build sets `STYLE_BODY_READ_TIMEOUT_MS`, the `app` start command refuses to run: it prints `STYLE_BODY_READ_TIMEOUT_MS is set in .env.production, where it is no longer read` and exits 1 before anything starts. The app therefore never becomes healthy, and the `worker`, `mailer` and `proxy`, which wait for a healthy app, do not start either, so the site is down rather than quietly running with 20 s instead of your old value. (An earlier draft guarded the worker; that left the app serving with the worker stopped, so it was replaced.) Remove the line from `.env.production`, put the value in the project `.env`, and run `docker compose up -d`. An empty `STYLE_BODY_READ_TIMEOUT_MS=` line is harmless and does not stop the app. Check with `grep STYLE_BODY_READ_TIMEOUT_MS .env.production` before upgrading. An old `STYLE_PROXY_BODY_READ_TIMEOUT_S` in `.env` from build 016 is ignored; delete it. Limit: a leftover under a different spelling, or set in the shell that runs Compose, is not a `.env.production` leftover (the shell value is simply the project variable).
- Outside Compose (local runs, tests) the app still reads `STYLE_BODY_READ_TIMEOUT_MS` from its own environment exactly as before. A bare `caddy run` with `deploy/Caddyfile` must set `STYLE_PROXY_BODY_READ_TIMEOUT_S` itself (22 pairs with the app default); the Caddyfile has no default, so an unset value fails to load instead of guessing.

**60 s probe: failure, then fix (root, local TLS loopback, app 60 s, proxy 62 s).** Direct and proxied 401 headers matched, health kept alive, counters returned 404, and a 1-byte-per-second trickle got the app's JSON 408 at 60.069 s with the socket closed. A **fully stalled** incomplete body got no response and no close within a 70 s watchdog. At 20/22 both modes had passed. Leading hypothesis: `read_body_idle` was left at Caddy's 1 m default, so for a stalled body it expires at about the same moment as the app's 60 s deadline (and a 120 s app setting would be cut at 60 s by it), while a trickle keeps resetting it; Caddy's own timer firing apparently produces no client response in this configuration. Direct check: the compiled app alone at 60 s answered a stalled body with its JSON 408 at 60.327 s, so the silence came from the proxy. Correction: `read_body_idle` is now set to the same derived value as `read_body`, so neither Caddy timer can fire before the app's 408. **Result with the correction (root, same local TLS setup, app 60 s, proxy 62 s, exit 0):** a stalled incomplete body got the app's original JSON 408 at 60.326 s with the socket closed at 60.330 s, before client cleanup; the 1-byte-per-second trickle got the JSON 408 at 60.327 s and closed at 60.328 s; the 401 body, content type and `Cache-Control: private, no-store` were identical to a direct request (the proxy adds `Connection: close`); health returned 200 twice over ALPN `http/1.1` with the second request reusing the socket; the upload counters returned 404. **Bounds:** the cause is the best explanation consistent with the direct result and the fix, not observed inside Caddy; 120 s (cap 122 s) has not been run live; nothing was run in Docker or on Linux; and what Caddy does when one of its own body timers fires first (a hung app) has not been tested, so the proxy timers must not be relied on as a backstop for an app that never answers. Values other than 20 s and 60 s are untested.

Raising it is a larger exposure: every stalled upload holds a connection for up to that long plus 2 s, and there is still no per-client connection limit. The strict check and the arithmetic are shell text that `tests/proxyConfig.test.ts` runs only where a POSIX `sh` exists; they have not run in the real Compose/Caddy images.

**Consequences of the numbers.** The proxy limit is on total time, so a legitimate upload slower than its share of that limit fails regardless of app settings: a 10 MB body (the proxy size cap) would need about 3.6 Mbit/s sustained for 22 s, the 3,000,000-byte wardrobe save about 1.1 Mbit/s. The app's own limits for each route still apply first (the wardrobe save is already described above at about 1.2 Mbit/s for 20 s). Slow mobile uplinks above these sizes are refused, not queued.

**Close-on-error cost.** Every error answer (including ordinary `401`, `404` and `429`) closes its connection, so the next request from that browser pays a new TCP and TLS handshake. Successful responses keep their connection (checked for health requests only, on the loopback candidate).

An earlier probe failed because of a wrong Host header; it was a probe error, corrected.
- **Scope limit.** This is one Windows loopback run with an untrusted internal certificate. It is not Docker, not Linux, not the Compose start guard, not a public domain or a publicly trusted certificate, not a real network path or phone, and not a repeated or loaded run. That replica ran the revision with an explicit `copy_response_headers`, which a later comparison showed duplicated upstream headers (next paragraph); the timing results above are therefore for a file that has since changed and must be re-measured.

**Error responses and their headers (corrected; one case measured, the rest NOT).** An earlier revision of this file added `copy_response_headers` on the assumption that `handle_response` does not copy upstream headers. That assumption was wrong, and root measured the result under local TLS: for an unauthenticated `GET /api/wardrobe`, direct from the app the 401 has `Cache-Control: private, no-store`; through that revision it had `private, no-store, private, no-store` (the same status, body and type). Reading Caddy's `reverse_proxy` source (v2.11.2, fetched, not run): nothing copies upstream headers to the client before `handle_response` routes run, and `copy_response` completes the response through Caddy's normal finalisation, which removes hop-by-hop headers and then **appends** every upstream header value. An explicit `copy_response_headers` therefore doubles each header. The route is now `header Connection close` followed by `copy_response` only; `Connection: close` set first is not undone, because the hop-by-hop headers are removed from the upstream copy. This is a source reading plus root's single measurement; the corrected file has not been re-measured, and `Retry-After`, `Content-Type`, `Content-Encoding` and `Set-Cookie` on 429/503/other errors have not been compared. Header comparison direct versus proxy remains a launch gate (below). The Caddy docs page does not spell out `4xx` class syntax for response matchers, `header` inside `handle_response` or connection handling during interception; the local replica exercised the 408 case only (the 401 and 413 refusals were measured earlier on a different candidate file), so the `4xx`/`5xx` match is shown working for 408 and nothing else through this file.

**Not verified, do not infer from this section (build 023 adds a CI smoke test for several of these items, described below; it has not been run yet):** the build 017 start commands in Docker (the strict millisecond check, the leftover refusal and the `+ 2 s` derivation in the `app` and `proxy` services; only a POSIX-`sh` copy of the text is exercised by the test file), Docker and Linux, a publicly trusted certificate and ALPN on the real domain, error-response headers through the proxy compared with direct (`Cache-Control`, `Content-Type`, `Retry-After`, `Content-Encoding`), a raised value through the real containers (for example 60000 giving a 62 s cap), concurrent stalled connections and any per-client limit (none is configured), a real slow or mobile link, the 3 MB wardrobe save through the proxy, the unchanged HTTP/2 problem (HTTP/2 is off, not fixed), and any launch-readiness.

**Probe after deploying (from a machine outside the server):** `curl -sv --http1.1 https://YOUR_DOMAIN/api/health` (expect 200, `alpn: http/1.1`); `curl -sI --http2 https://YOUR_DOMAIN/api/health` (expect HTTP/1.1 in the status line); `curl -s -o /dev/null -w '%{http_code}\n' https://YOUR_DOMAIN/api/health/uploads` (expect 404); then a stalled-upload probe that sends headers with a large declared `Content-Length` to an upload route, sends nothing more, and records when the 408 and the socket close arrive (expect about 20 s and 20 s, not more than 22 s; no reply at 35 s means this change failed).

### Compose + Caddy smoke test (build 023; AUTHORED, NOT RUN until the first Docker CI job passes)

`scripts/ci-compose-smoke.ts` is a CI-only check of the **shipped** `compose.yaml` and `deploy/Caddyfile` in real containers. It is a step of the Docker job in `.github/workflows/ci.yml` (after the build 022 drill) and runs locally on a Docker host with `docker build -t style-studio:ci . && npm run ci:compose-smoke` (it needs a Compose release that understands the `!override` merge tag; the runner checks and stops with a message otherwise, and this guide names no minimum version). **It has not been run by the author: Docker was not available. Treat every claim below as a description of what the step checks, not as a result, until the first CI run has passed.**

**How it stays faithful.** It copies `compose.yaml` and `deploy/Caddyfile` byte for byte into a throw-away project folder and adds `deploy/ci/compose.smoke.yaml`, which changes only: the image of `app` (`style-studio:ci`, the only image built from this checkout; the `app` is started with `--no-build` and that image is never pulled), `restart: "no"` (so a refused start stays visibly stopped), the proxy's published ports (`127.0.0.1:18080` and `127.0.0.1:18443` instead of 80 and 443) and the model (the build 008 mock, no download). The runner compares `docker compose config` with and without that file and fails if anything outside that list differs, so the start commands, healthchecks, environment, mounts, `security_opt` and `cap_drop` of `app` and `proxy` are the shipped ones. (The one top-level difference allowed is the `model-data` volume being absent from the merged output: nothing mounts it once the mock model replaces `ollama`'s mounts, and `docker compose config` leaves unused volumes out. A changed or added volume, or any other volume going missing, still fails.) Only `app` and `proxy` (and the mock model that `app` waits for) are started, never the worker or the mailer. The other images, `caddy:2` and the `node:24-bookworm-slim` that runs the mock model, are not built here and may be pulled from a registry on first use; the smoke test does not claim to run without network access to a registry. The mock model's mount path in the override is relative to the throw-away project folder (the runner copies the mock there), so the override is not meant to be used from the repository root. If you run the smoke test on a host that also runs production services, those keep running: every smoke resource is named `style-smoke-<run id>`, and the loopback ports 18080 and 18443 must be free. The project `.env` and `.env.production` are generated per run: a random `AUTH_SECRET`, a placeholder `SMTP_URL` nothing connects to, and a 200 ms auth lock wait (`STYLE_AUTH_LOCK_MS`) used by the busy test below.

**TLS without a public domain.** The site name is `style-ci.localhost`. Caddy serves `*.localhost` names from its own internal CA, so no public certificate authority and no account is involved, and the application accepts it as a public `APP_URL` (it refuses the exact name `localhost`). The test trusts only Caddy's own root certificate, read from the proxy container. This says nothing about a publicly trusted certificate, ACME, DNS, or your real domain.

**What it checks.**
- *Timeout wiring, default 20000:* the running server process has `STYLE_BODY_READ_TIMEOUT_MS=20000`, the proxy's PID 1 has `STYLE_PROXY_BODY_READ_TIMEOUT_S=22`, and Caddy's running configuration shows a 22 s body timeout, a 10 s header timeout and `h1` only. A stalled upload through the proxy gets the application's own 408 (`took too long`), after about 20 s and before the 22 s cap, with `Connection: close` and a closed socket.
- *Raised value:* with `STYLE_BODY_READ_TIMEOUT_MS=30000` in the project `.env`, `docker compose up` recreates the containers; the same checks expect 30000, 32 s and a 408 after about 30 s.
- *Fail closed:* `abc`, `0999`, `999`, `20000s`, `1e4`, `130000` and `1234567` make both the `app` and the `proxy` start commands exit 1 with the shipped message, and neither starts. Through `docker compose up`, an invalid project value, and a stale `STYLE_BODY_READ_TIMEOUT_MS=30000` line in `.env.production`, leave the app exited with code 1 and its message; the proxy, worker and mailer are not running. An empty `STYLE_DOMAIN` stops the proxy; an empty `STYLE_BODY_READ_TIMEOUT_MS=` line falls back to 20000 (documented behaviour, not an error).
- *Proxy behaviour:* ALPN picks `http/1.1` when `h2` is offered; two health requests share one connection and carry the five Caddyfile security headers exactly once; plain HTTP redirects to the HTTPS site; `/api/health/uploads` (with a trailing slash, a sub-path or a query) is 404 through the proxy while the app answers it directly, and an upper-case, a percent-encoded and a double-slash spelling are not served.
- *Direct versus proxied errors:* for 401 (wardrobe without a session), 403 (change without the app origin), 404 (unknown route), 413 (oversized account request) and a 503 with `Retry-After: 5` (produced by holding SQLite's write lock from inside the app container while a sign-up is sent), the status and body must be identical, every header the app sends must arrive with identical values (this catches a duplicated `Cache-Control`), the proxy may add only `Server`, `Via` and the five Caddyfile headers, and the proxied error must say `Connection: close`.

**Cleanup and logs.** Everything is named `style-smoke-<run id>`. A `finally` runs `docker compose down -v --remove-orphans`, then removes any container, volume or network still carrying that name, deletes the project folder (which holds the generated secret), and fails the run if anything remains. An `if: always()` step sweeps all `style-smoke-` resources, and the redacted service logs are uploaded as the `compose-smoke-logs` artifact. The run fails if `AUTH_SECRET` appears in any docker argument, output or log.

**What it does not show.** A public domain, a publicly trusted certificate, ACME, HTTP/2 or HTTP/3 (off by design), a real browser, a real mobile or slow link, concurrent stalled connections, the 3 MB wardrobe save through the proxy, a 120000 ms setting, the `worker` and `mailer` containers, SMTP delivery, any real model, `restart: unless-stopped` and production port 80/443 binding (the override changes these), Docker or Compose versions other than the runner's, or any launch readiness. It also does not change production: `compose.yaml`, `deploy/Caddyfile` and the `Dockerfile` are untouched by build 023. One thing it does not fix: the `app` start command in `compose.yaml` ends with `&& node server.js` (no `exec`), so `docker compose stop` signals a shell, not the server, and waits out Docker's stop timeout; the build 022 drill uses `exec`.

Monitor disk space, memory, mail failures (`mailer` health and `--status` counts), worker heartbeat and queue saturation. Never log passwords, verification links, session tokens, wardrobe photos or AI image payloads. Keep server patches and container digests under review. This folder does not contain a purchased domain, hosting account or mail-provider account; those external setup steps remain outstanding.
