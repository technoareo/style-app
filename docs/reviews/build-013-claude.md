## 3. Audit of the code [Code-proven unless marked]

### 3.1 Admission (`admission.ts`)

- **Order** (`:172-190`): same-owner check (429, takes nothing, counts `refused`) -> synchronous capacity check -> `holders.add` -> `withImageWork` -> `finally` delete. `withImageWork` calls `acquire` synchronously (async function runs to its first `await`), so the holder set and the semaphore are updated in the same tick. The bound `holders.size >= imageConcurrency + imageQueue` (`:181-182`) therefore holds after **every** launch, which the 100-launch test asserts per iteration (`accountUpload.test.ts:364-377`). This closes the initial failure (peak 100 vs 3).
- **Why the bound is sufficient:** every holder is active (<= concurrency), queued (<= queue) or in the few microtasks between the global release and `holders.delete`. A zombie in that window can only make the check refuse **early**, never admit extra. Disclosed in the notes; harmless.
- **Queued abort** (`:65-97`): a pre-aborted caller that would have to queue is rejected before joining (`:71`); an abort while queued removes the waiter, clears its timer and rejects 400. Listener removed on grant and on wait timeout; `once: true`. The waiter's `reject` field is unused by that path but harmless. If a waiter is granted and aborted in the same tick, `onAbort` returns early (`index < 0`) and the body reader sees the aborted signal; no leak.
- **Release coverage:** token is deleted in `finally` on success, thrown error, body timeout/abort/oversize, decode failure, wait timeout and queue-full. The routes await the guard to completion before `runWriteTransaction` (static source test `:438-452`, plus my reading of `photos/route.ts:67-86` and `analyze/route.ts:54-79`). No database call is inside the guard.
- **Token scope:** keyed by authenticated `session.user.id`, after origin, session and account-binding checks (`access.ts:56-89`). One account cannot cause another account's 429.
- **Global state:** `Symbol.for` on `globalThis`, like the existing semaphore; the account set holds opaque ids in memory only, never logged or returned (checked in `uploadMetrics.ts` and the health route).

### 3.2 Bounded body (`boundedBody.ts`)

- **Wake-up:** each read gets its own promise (`:236-246`); `wakeRead` is set in the executor and cleared in `.finally`. `stoppedReason()` is evaluated synchronously immediately before `readOnce()` (`:259-264`), so a stop cannot fall between the check and the registration. After a stop, a still-pending `reader.read()` settles an already-settled promise; its rejection is consumed by `.then(resolve, reject)`, so no unhandled rejection. `!raced` is reachable only after a stop (only `stop()` calls `wakeRead`), and the `after` check returns before `break`, so a partial body cannot become `ok` through that path.
- **Deadline, caps, abort, cleanup, 250 ms cancel grace, statuses:** unchanged from build 012 by reading (I compared against my 012 audit). The clock checks before/after each read and before `ok` remain.
- **Collector** (`:84-137`): chunks under a quarter slab are copied into slabs; larger ones are kept by reference after sealing the slab, so order is exact; zero-byte chunks are dropped; a mostly empty slab is copied out. Retained **pieces** are bounded by about `2 x maxBytes / direct` (<= ~360 at 3 MB). Cap is checked on `size` before `add`.
- **Counters:** every outcome goes through `countBody` in `readBoundedBody`; every cancel through `countCancel` in `giveUp`. A genuine stream error counts `error` and rethrows. One nuance: `giveUp` sets `finished = true` only after the awaited cancel, so a throw inside `abandon` is impossible (it swallows), fine.

### 3.3 Metrics and privacy shape (`uploadMetrics.ts`, health route)

- Closed label sets (5 routes; 6 body outcomes; 3 cancel outcomes; 3 account events); unknown route -> `other`; unknown outcome ignored (`indexOf < 0`). State is fixed arrays of integers, ~5 x 12 numbers. `uploadMetrics()` returns fresh plain objects. The health route returns fixed keys only, `Cache-Control: no-store`, no query parameter used, no database or auth call. No id, email, IP, header or error text can reach it. The test walks the JSON for integers, key order and absence of the account id/email (`accountUpload.test.ts:454-507`). I accept the fixed privacy shape.
- It is **unauthenticated and the shipped Caddyfile does not block it** (finding S2).

### 3.4 Client retry (`serverRepository.ts:48-73`)

- Only `ApiError` with `code === "upload-in-progress"` is repeated, up to 3 times, after `min(5, max(1, retryAfter ?? 3))` seconds; 408, 409, 413, 503 and everything else are thrown at once. Retrying is safe because a refused 429 stored nothing and the server de-duplicates by content hash. The `/api/analyze` call from `UploadDialog` is **not** retried (it shows the server's sentence, line 434 by grep). The worst case wait is 15 s, shorter than the 20 s a stalled holder can last, so a persistent conflict can still surface to the user (acknowledged in the notes).
