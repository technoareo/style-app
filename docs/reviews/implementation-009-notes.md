## 1. C1: mail worker health and shutdown

### Heartbeat
* `src/server/mailHealth.ts` (new): `createMailHeartbeat`. A timer of the worker's own writes the beat every `STYLE_MAIL_HEARTBEAT_MS` (default 10 s).
  * It runs on the event loop, so a process whose loop is stalled stops reporting.
  * It writes only while the worker loop reported **progress** within `stuckAfterMs`. The worker passes `mailStepBoundMs() + 15 s` = max(send timeout + 3 s grace, 10 s claim budget, record try + pause) + 15 s (63 s with defaults). A loop alive but wedged on a promise that never settles also stops reporting.
  * No overlap: while a write is in flight further ticks do nothing (`skipped-busy`); each write is bounded by `touchMailHeartbeat`'s own 5 s acquire budget. A failed write is retried on the next tick.
* `processNextMail` calls `onProgress` at the start and end of every bounded step (before claim, after claim, after the send, after each record try, and on return). The idle loop reports progress every pass.
* `--check` uses `healthFreshMs` = `max(STYLE_MAIL_HEALTH_FRESH_MS (60 s), 3 × heartbeat)`.
* This removes the 008 failure: a healthy worker working through 20 slow sends no longer goes stale.

### Shutdown
* Trigger: SIGTERM, SIGINT, or the IPC message `"shutdown"` (the portable trigger the tests use; Windows cannot deliver SIGTERM to a child).
* `processNextMail({ shutdown })`: nothing is claimed once aborted. A send in flight is cancelled through the **same `AbortSignal` that already carries the deadline** into `deliverMessage` → `sendOverSmtp`, which destroys every socket of that attempt (plain, TLS and a STARTTLS wrapper). No new mechanism, no second path to the socket. Cause is tracked (`deadline` vs `shutdown`); a shutdown stop is reported as `EMAIL_SHUTDOWN`.
* Outcome `released` (new `finishMailLocked` branch): `status='queued'`, `attempts=MAX(attempts-1,0)` (a cancelled send is not a failed attempt; the 5-attempt bound stays exact), `last_error_code='shutdown'`, `next_attempt_at=now`, `lease_until=NULL`. Same guard as every outcome: status `sending` **and the exact lease**, so an expired, superseded, deleted or re-claimed row records nothing. Address and bodies are kept (the message is still deliverable); expiry still applies. A send that completed before the cancel took effect is recorded **sent**.
* Record budget once shutdown has started: `STYLE_MAIL_SHUTDOWN_RECORD_RETRIES` (2) tries of `STYLE_MAIL_SHUTDOWN_RECORD_ACQUIRE_MS` (2 s) with 250 ms pauses; re-evaluated on every try, so shutdown beginning mid-record shortens it. Normal record bounds are unchanged: 8 retries of 5 s with 500 ms pauses (now configurable, same defaults).
* If the record still fails the row stays `sending` and **lease recovery** returns it to the queue (lease = send timeout + 60 s). Duplicate delivery is possible then, as before.
* Worker exit: loop ends, heartbeat stops, databases close, `process.exit(0)`. A hard-exit timer (`STYLE_MAIL_SHUTDOWN_EXIT_MS`, 25 s, exit code 1) abandons anything still running.
* Worst bounded work after a request, defaults (`mailShutdownWorstCaseMs()`): 16.5 s (10 s claim budget + 3 × 2 s + 2 × 250 ms; during a send 3 s grace + 6.5 s; during a normal record try 5 s + 0.5 s + 6.5 s). 16.5 s < 25 s hard exit < 40 s `stop_grace_period`. `tests/mailWorker.test.ts` asserts all three relations.
* `compose.yaml` (`mailer`): `stop_grace_period: 40s`; command and health check now `node --import tsx scripts/mail-worker.ts` so node is PID 1 and gets SIGTERM directly (the tsx launcher would sit in between). **Never run in Docker.**
* Preserved: at-least-once, `attempts` accounting, FK cascade, the write gate (all writes still go through `runWriteTransaction`), every 008 bound, log text (only a fixed "interrupted by shutdown" line with the message UUID, no address, body or link).

### New configuration (all validated; out-of-range values fall back to the default)
`STYLE_MAIL_HEARTBEAT_MS` 10000 (50–60000); `STYLE_MAIL_HEALTH_FRESH_MS` 60000 (150–600000, raised to 3 × heartbeat); `STYLE_MAIL_RECORD_RETRIES` 8 (0–20); `STYLE_MAIL_RECORD_ACQUIRE_MS` 5000 (100–30000); `STYLE_MAIL_SHUTDOWN_RECORD_RETRIES` 2 (0–5); `STYLE_MAIL_SHUTDOWN_RECORD_ACQUIRE_MS` 2000 (100–10000); `STYLE_MAIL_SHUTDOWN_EXIT_MS` 25000 (500–120000).

## 2. C2: failure-safe, serialised backups

Code: `src/server/backupDatabase.ts` (new, all logic), `scripts/backup-database.ts` (thin), `tests/helpers/backupChild.ts`.

* **[Superseded by section 10: the lock below is replaced; it was refreshed from the event loop and a blocked live owner lost it.]** **Serialisation (root's feedback).** A `proper-lockfile` lock (`backups/.backup.lock`, stale after 60 s without refresh, refreshed every 10 s, 30 s wait in 500 ms polls) is held from before the first step to after the last. Backups in different processes or containers on the same volume therefore never overlap, and the name check and the rename cannot interleave. A lock lost mid-run (`onCompromised`) makes the backup refuse to publish.
* **No overwrite.** The final name is chosen **under the lock**: `style-<stamp>.db`, or `style-<stamp>-<n>.db` (digits only, so it stays inside the restore pattern `^style-[0-9TZ.-]+\.db$`) if that exists. A name that exists is never replaced.
* **Stale partials (root's feedback).** Age alone is not used. A partial is swept only **while this process holds the lock**, which proves no backup is running, so everything found belongs to a dead process. A partial behind a live lock is never touched (a second backup fails with "Another backup is running", leaving it alone).
* **Stages.** `backup()` → `<stamp>.<12 hex>.partial` (does not match the restore or retention patterns) → sanitise in one `BEGIN IMMEDIATE` transaction with `secure_delete=ON` (`analysis_jobs`, `mail_outbox`, `verification`, `session` emptied; `worker_state`, `mail_worker_state` dropped) → `VACUUM` → `wal_checkpoint(TRUNCATE)` → `journal_mode=DELETE` → verify (integrity, foreign keys, the four tables empty) → close → remove any sidecar → fsync (best effort) → choose name → atomic `rename`. Prune (7 days) only after the rename.
* **Cleanup is observable (root's feedback).** Every removal returns whether the name is really gone. A caught failure throws `BackupFailure` with `leftovers` naming any partial or sidecar that could not be removed; crash leftovers that cannot be swept are returned in `BackupResult.leftovers`. The script prints the names (fixed pattern, no user data) and exits **2** (done but a file needs hand removal; also for a failure plus a stuck leftover, message first says it failed), **1** failed with nothing published, **0** done. The old unconditional "no partial" claim is gone.
* **Physical guards kept and extended.** Backups directory must be a real directory, not a link, and its `realpath` equal its path (`lstat` + `realpath`); every touched name is built from it plus a generated or fixed-pattern-matched name; no recursive deletion; a link carrying an owned name is unlinked as a link (`unlink`, falling back to `rmdir` for a Windows junction) and its target is never entered; directories with owned names are left alone and reported. The live `app.db`, `-wal` and `-shm` are in the data directory and are not candidates.
* **Truth while a partial exists.** The raw, **unsanitised** copy exists in the 0700 backups directory during the run and after a kill. README and DEPLOYMENT now say so, say that only `style-*.db` may be copied off the server, and give the exit codes.
* Preserved: prior valid backups (byte-identical in the tests) and the live database are never modified by a failed run.

## 3. C3: password-revival protection on the existing restore

> **Current state of the backup lock (read this, not the older text in 10.1 or section 2):** ownership is an **operating-system file lock (a SQLite `BEGIN IMMEDIATE` reservation) held by the backup process on `backups/.backup-coordinator.db`**, released by the OS the instant the process ends. There is **no lease, no refresh, no keeper thread, no stale/age judgement and no takeover rename**; `proper-lockfile` is no longer used for backups. Sections 10.1 and 2 describe the earlier designs and are kept only as history of what was wrong. See 10.4 for the design and 10.6 for the latest test fixes.

### 10.1 Backup lock: a live owner must never look dead (P1, reproduced by root) — **the keeper-thread/lease design below was itself superseded by 10.4; the publication, guard and test parts still stand**

**Cause (agreed).** `proper-lockfile` refreshed the lease from a timer on the owner's own event loop and declared the lock compromised when that timer ran late. A long synchronous step (VACUUM, `integrity_check`) in the owner stops the timer, so after 60 s a second backup took the lock, deleted the first one's active partial and succeeded, and the first then failed. Raising the lease or yielding a microtask would only move the threshold, and, as root says, age was being trusted as death.

**Strategy: a lock whose liveness does not depend on the owner's event loop** (`src/server/directoryLock.ts`, new; `proper-lockfile` is no longer used for backups, it remains for `schema.lock`).
* The lock is the directory `backups/.backup.lock` made with `mkdir` (atomic), holding one `owner` file with a random token.
* A **keeper thread** (`worker_threads`, eval'd plain JS so no TypeScript loader is involved) does nothing except refresh the lock's modification time every `refreshMs` (5 s), after checking the owner file still holds this holder's token. It runs whatever the main thread is doing, including a main thread blocked for minutes in native code, and it dies with the process. So: **alive process ⇒ fresh lease; killed or crashed process ⇒ lease lapses `staleMs` (60 s) later.** Age is read only as "no thread of the owner has refreshed this for 60 s", never as a standalone death proof. The refresh interval must be at most a quarter of the lease (enforced).
* Takeover of a lapsed lock: `rename` of the lock directory to a unique `.backup.lock.stale-<12 hex>` (atomic, one winner), then its owner file and the directory are removed. Taking over also lets the new holder sweep the dead owner's partial.
* Before publishing, `assertHeld()` re-reads the owner token and the lease age; a lost lock refuses to publish.
* **Publication cannot overwrite** (defence in depth, root's earlier concern): the finished partial is published with a hard `link` to the final name (fails with EEXIST instead of replacing), then the partial name is unlinked; the next free name (`-1`, `-2`, …) is used on collision. Where hard links are unavailable it falls back to check-then-rename under the lock. If the partial was already removed (lock lost) the publish fails with ENOENT and nothing is published.
* Physical guards kept: the backups directory must be a real directory with `realpath` equal to its path; the lock path must be a plain directory (a link is refused); every removal is by generated or fixed-pattern name, no recursion, a link with an owned name is unlinked as a link; own-partial cleanup, `BackupFailure.leftovers`, exit codes and prune-after-success are unchanged.
* **Residual cases (documented in DEPLOYMENT.md):** a whole-process freeze longer than the lease (SIGSTOP, VM pause) stops the keeper too and can lose the lock; the frozen owner then fails (`assertHeld` or the missing partial) and publishes nothing. A live owner stuck forever holds the lock forever (kill it; the lease lapses 60 s later). The lease compares file times with the local clock, so `/data` should be a local volume. Not tested on a network file system.
* **What this does not claim:** it does not measure how long a real VACUUM takes on the target host, and it does not move VACUUM off the main thread; it makes the length of that step irrelevant to ownership.

**Tests (written, not run by me)** in `tests/backupSafety.test.ts`, with a shortened lease (2 s lease, 200 ms refresh; same refresh ≤ lease/4 relation as production 60 s / 5 s):
* *Killed owner, for real:* the child reports the raw-copied stage over IPC and waits; the **parent kills it with SIGKILL** (TerminateProcess on Windows), so no exit hook, signal handler or cleanup runs (the 009 fixture used `process.exit(9)`, which ran `proper-lockfile`'s own exit cleanup and removed the lock; the helper no longer has a kill-by-exit mode). The parent waits 4.5 s, asserts the partial is still there, asserts a second backup is **refused** and did not remove the partial, then the owner wakes, exits 0 (`doneAt − rawCopiedAt ≥ block`), its final file exists, no partial, no markers, no lock left, and the lock is then free for the next backup.
* *No overwrite at the last moment:* a file with the intended final name appears after verification (stage hook); the backup is published as `…-1.db` and the late file is byte-identical.

### 10.4 Second correction: ownership by an OS lock, not by age (root's takeover race)

**Finding (accepted).** `docs/verification/directory-lock-takeover-009.json`: contender B read the lock's age with `lstat`, paused, owner A took the (just lapsed) lock and was refreshed, then B resumed and `rename`d the *current* lock path, taking A's fresh lock (`secondAcquired`, `freshFirstOwnerLost`). The keeper thread fixed event-loop starvation but not the real flaw: a decision made from an old observation of a timestamp, applied to whatever is at the path now. I do not claim any timestamp proves an owner dead; none is used any more.

**Design (`src/server/directoryLock.ts`, rewritten; same file name).**
* The lock is a SQLite write reservation (`BEGIN IMMEDIATE`, held for the whole backup) on a dedicated, empty coordinator database `backups/.backup-coordinator.db`, opened with a zero busy timeout. SQLite implements it with the platform file lock (fcntl / LockFileEx). The kernel grants it to one process at a time and **releases it the instant that process ends**, however it ends. Contenders just ask ("lock me now"): the answer is yes or busy, atomically, at that moment. There is no lease, no refresh, no keeper thread, no `stale` state, no takeover rename and no lock directory, so there is nothing a paused contender can act on later.
* Independent of the application: a different file from `app.db` and none of its write gate or `BEGIN IMMEDIATE` on the live connection. A backup never waits for, or blocks, application writes through this lock, and the application never takes it.
* Behaviour: live owner (even with its main thread blocked for minutes): holds it, others get `Another backup is running` after `lockWaitMs` (30 s by default; polled every 100 ms). Killed or crashed owner: free at once. Two contenders for a freed lock: the kernel picks one, the other keeps waiting and gets it only after the first releases. A frozen-but-alive process keeps the lock (documented; kill it). Holding the lock is the only proof used that no live backup exists, so partials found while holding it belong to dead processes and are swept.
* `assertHeld()` before publishing only catches a programming error (released or closed). Publication is still no-overwrite (hard link, next free `-n` name) as defence in depth if a volume's file locks were ever unreliable.
* Physical guards: the coordinator path is built from the verified backups directory; a link or non-regular file there is refused (`lstat`); it is never written, never deleted by the backup, never recursive; all earlier partial/sidecar rules are unchanged (own fixed-pattern names, link unlinked as a link, directories left and reported, never the live `app.db`/`-wal`/`-shm`, which are not in `backups/`).
* **Limits, stated:** SQLite locks are reliable on local volumes and unreliable on NFS/SMB; the whole scheme assumes a local volume (documented in DEPLOYMENT.md). On POSIX, closing any other descriptor for the same file inside the owning process would drop the lock, so the coordinator file is opened in exactly one place and nothing else touches it. Not exercised on Docker, on a network file system, or on Linux/macOS by me; root's runs are on Windows.
* Removed: `proper-lockfile` for backups (still used for `schema.lock`), the keeper worker, `lockStaleMs`/`lockRefreshMs` options and the matching test env variables.

**Tests (written, not run by me; `tests/backupSafety.test.ts`, `tests/helpers/backupChild.ts`).** No time compression is needed any more: nothing depends on a lease.
* *Genuine kill and reclaim:* the parent SIGKILLs an owner at its raw-copied stage (IPC signal; no exit hooks run). While it lived, a second backup was refused and its partial untouched. After the kill: no final file, one partial that restore refuses, live DB untouched; the next backup takes over **without waiting for any lease** (< 5 s allowed only for OS teardown), removes the dead partial, no marker bytes remain.
* *Two contenders and a live owner:* an owner is blocked holding the lock; two other backups start and wait (asserted not started after 4 s); the owner's partial is intact. The owner is killed; both contenders succeed **one at a time** (second's raw copy after the first is done, both started before the first copied), neither before the kill, the dead partial removed, two backups, no partials, no markers. This is the takeover race's shape (two waiters, a live owner, a release) under the new semantics.
* *Blocked main thread:* a live owner blocked 7 s in native code keeps lock and partial, a second backup is refused (partial untouched), the owner finishes normally, the lock is then free.
* *Lock module:* a second holder is refused while the first lives (even in the same process), a waiter is granted only after release, `assertHeld` fails after release, a coordinator path that is a link is refused with its target untouched (skipped where links cannot be created).
* Unchanged and still relevant: same-millisecond overlapping processes (existing file untouched, `-1`/`-2` names), last-moment name collision, failure at every stage, observable cleanup failure, pruning after success, link guards.
* *Keeper failure:* not applicable, the keeper no longer exists.
* **Unverified, check first:** `tsc`; that node:sqlite's busy error carries `errcode` for `BEGIN IMMEDIATE` on a second connection to the same file in the same process (`isSqliteBusy`); that a SIGKILLed child's lock is released promptly on Windows; the contender test's 4 s wait is long enough for both children to start under load (it only asserts they have *not* reached the copy stage, so a slow start can only make the assertion easier to satisfy, not fail it, but also weaker).
