## 1. Wardrobe GET: read first (`src/server/wardrobes.ts`, `src/app/api/wardrobe/route.ts`)

**Before.** GET ran `loadWardrobe` inside `runWriteTransaction`: every read took the process write gate and `BEGIN IMMEDIATE`, and called photo reclamation even for an empty wardrobe.

**Now.**

- `readWardrobe(userId, name)` is a plain synchronous read. No gate, no BEGIN, no write. A missing wardrobe returns `{version:1, name, wardrobe:[], looks:[], revision:0}` and **no row is created**. `readWardrobeAsync` wraps it in `retryBusy` (2 s) for a transient SQLITE_BUSY and maps a persistent busy to the existing retryable 503 (`WriteContentionError`).
- The read also returns `reclaimable`, a **hint**: some photo older than 24 h belongs to the user and the returned document does not reference it. It is computed from one extra indexed `SELECT id` (blobs are not read). It authorizes nothing.
- Only when `reclaimable` is true does GET call `reclaimAfterRead(userId)`. That runs `reclaimExpiredPhotos`, one `runWriteTransaction` with a 2 s budget (`RECLAIM_ACQUIRE_MS`). Its body, `reclaimExpiredPhotosInTransaction`, **re-reads the current `wardrobe_spaces` row inside the committing transaction** and deletes only expired photos that row does not reference. It takes no references from the caller, so there is no stale-snapshot path to misuse.
- Fail closed: if the stored document is missing, unparsable or not shaped like a wardrobe (`wardrobe`/`looks` not arrays, a look without `items`), the reclamation deletes **nothing**. "I could not read the references" must never look like "nothing is referenced". A missing row (no wardrobe) is the one legitimate empty set, and it still creates no row.
- One reclamation per account at a time (`inflight` map); a concurrent caller joins it. Failures (gate timeout, busy, anything) are swallowed. The response never depends on the outcome, and the next read that still sees an expired photo asks again.
- Other accounts' photos are never touched (`user_id` is in every statement).

**Decision to flag: GET awaits the bounded cleanup rather than firing it after the response.** The existing test `tests/accounts.test.ts` (around line 156) calls `GET` and immediately asserts that an expired orphan is gone. A fire-and-forget cleanup would make that assertion racy, and I was told to preserve existing tests. The cost: the rare GET that finds something to reclaim can wait up to 2 s under contention. The common GET (nothing to reclaim) waits for nothing. If root prefers response-first cleanup, the change is one line in the route (drop the `await`), plus an adjusted accounts test that polls.

**Compatibility.**

- `loadWardrobe(userId, name)` and `saveWardrobe(userId, input)` keep their exported names and synchronous, transaction-joining behaviour for any direct caller. `loadWardrobe` is now `readWardrobe` plus `reclaimExpiredPhotosInTransaction` in one `inTransaction`. The route no longer calls it.
- Response bytes for GET are the same objects as before (same fields, `revision` last).

- `commitWardrobeSave(userId, prepared)` runs inside the one committing transaction (joins the route's `runWriteTransaction`, or opens its own): per-photo existence **and ownership for this user**, the revision comparison, the byte-identical idempotent acknowledgement, the upsert, and reclamation of photos the replaced and the current documents leave unreferenced. The replaced document is read inside the transaction. No `await` anywhere in it.
- Route order is unchanged up to the body: `account(req, true)` (origin, session, binding, quota) → `readJson` → **`prepareWardrobeSave`** → `runWriteTransaction(commit)`. Authorization is not bypassed; an unauthenticated request never reaches parsing.
- `saveWardrobe` = prepare then commit, so direct callers see the same results.

**Behaviour differences (all 400/413 with static messages):**

1. A document that is both over 3 MB and references an unavailable photo now answers 413 (before the gate) instead of 400. A pure rejection (data URL, external URL) is now thrown before any database check.
2. Photo existence is queried once per distinct id instead of once per use.

**Not moved, deliberately:** the `JSON.parse` of the replaced document stays inside the transaction because it must be the document that is current at commit. It is a cost inside the hold for a large wardrobe. Measuring it is an open item.

## 3. Auth dialect: one deadline (`src/server/authDialect.ts`)

- `begin()` records `deadline = t0 + acquireTimeoutMs` before waiting for the gate. The gate wait still uses the full budget as its own timeout (so a stuck gate fails at the budget). After the gate is granted, `BEGIN IMMEDIATE` is retried with `max(0, deadline − now)`. With zero remaining there is still exactly one attempt, as on the write path. The budget value is unchanged (`STYLE_AUTH_LOCK_MS`, default 10 s). Nothing was raised or shortened.
- The shared `Retry` closure takes an optional per-call timeout. Autocommit statements via `executeQuery` still get their own full `acquireTimeoutMs`, as before (they are not part of begin).
- Failure path unchanged: the gate is released before the error propagates; the original SQLite error object is rethrown with the `acquire` detail attached. That detail and the `AcquireEvent` shapes are numbers only and unchanged; only the **meaning** of `budgetMs` on the auth path changed (one shared budget). I updated the comments in `lockDiagnostics.ts`, `auth.ts` and the `authDialect.ts` header. The older note `docs/reviews/implementation-011-notes.md` line 47 still describes the pre-015 meaning; it is a historical record and I did not edit it.
- Single-use token safety is unchanged: BEGIN IMMEDIATE is still taken before the body's first read, and the body is never replayed. I did **not** change hashing, the Better Auth handler, or where hashing runs. Hashing still spans the write transaction (see unresolved items).
