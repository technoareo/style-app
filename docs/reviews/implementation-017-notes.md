### Problem
Build 016 paired two variables by hand: the app's `STYLE_BODY_READ_TIMEOUT_MS` (in `.env.production`) and the proxy's `STYLE_PROXY_BODY_READ_TIMEOUT_S`. An operator who raised the first and forgot the second had real uploads cut by Caddy at 22 s, silently. Also the app ignores an invalid value (`src/server/limits.ts` `int()` falls back to 20000; accepts `" 20000 "`, `2e4`, `0x4e20`), so a proxy that parsed the raw string could disagree with the app.

### Design
- **One non-secret project variable** `STYLE_BODY_READ_TIMEOUT_MS` (project `.env`, shell or `--env-file`), default 20000 in `compose.yaml` as `${STYLE_BODY_READ_TIMEOUT_MS:-20000}`, written identically in the `app` and `proxy` `environment:`. The proxy still has no `env_file`.
- **Proxy derives the cap at start:** `STYLE_PROXY_BODY_READ_TIMEOUT_S=$(( ($X + 999) / 1000 + 2 ))` exported before `exec caddy`. Values: 1000 -> 3, 20000 -> 22, 20001 -> 23, 60000 -> 62, 120000 -> 122. The space after `$((` avoids the `$(((` ambiguity.
- **Strict validation, same text in `app` and `proxy` commands:** `case` rejects empty, a leading `0`, any non-digit, and lengths 1-3 or 7+; then `[ "$X" -gt 120000 ]`, evaluated only after the case accepted a 4-6 digit number, so no overflow, octal reading or `[` error can slip through (the build 016 guard had that hole for long numbers, fixed in revision). Failure prints a fixed message and exits 1: the container restarts visibly and the proxy never starts with a guessed cap.
- **`deploy/Caddyfile`:** `read_body {$STYLE_PROXY_BODY_READ_TIMEOUT_S}s` with **no default**. Under Compose it is always derived. A bare `caddy run` or `caddy validate` must set it (root's harness already sets 22). An unset value makes Caddy fail to load rather than silently choose a number.
- **(Superseded by Revision 2 below: the guard is now in the app, under a different container variable name. The text in this bullet and the worker items in "Tests" and "Threat" describe the first draft.) Migration from `.env.production`:** the `app` `environment:` entry overrides `env_file`, so an old value there would be silently ignored (reset to 20 s). The `worker` (which never reads the variable and has no `environment:` entry for it) now starts with `sh -c 'if [ -n "$STYLE_BODY_READ_TIMEOUT_MS" ] ...; exec ...analysis-worker.ts'` and refuses with a message when the variable reaches it from `.env.production`. `exec` keeps the launcher as PID 1. The `mailer` is not guarded (its PID 1 requirement from build 009).
- **No application source change.** Local non-Compose runs and every test that sets `process.env.STYLE_BODY_READ_TIMEOUT_MS` behave as before.
- **Template:** `.env.compose.example` keeps exactly one active assignment (`STYLE_DOMAIN`); the new variable is a commented line with the rules.

### Revision 3: 60 s stalled-upload failure (config, test, docs; NOT executed)

Root (local TLS, current Caddyfile, app 60 s, proxy 62 s): trickle got the app's JSON 408 at 60.069 s and closed; a fully stalled incomplete auth body got neither a reply nor a close within 70 s; 20/22 had passed in both modes; 401 headers matched direct, keepalive, counters 404 fine. Root is checking the app directly at 60 s.

Analysis (reading Caddy docs and Go's server behaviour; not run): Caddy's `read_body_idle` is a stall timer that resets on each read and defaults to 1 m; `read_body` is the total cap and bounds it. The Caddyfile set only `read_body`. For an app deadline of 60 s the default idle timer for a body that never sends a byte expires at about the same instant as the app's deadline (its clock starts when Caddy begins reading the body, slightly before the app's), and with a 120 s app setting it would always win. A 1 byte/s trickle keeps resetting the idle timer, so only the app's deadline remains, matching the result. At 20 s the app's deadline (20 s) is shorter than the 1 m idle timer, matching the earlier passes. The same reading suggests that when a Caddy body timer fires first on this path the client receives nothing (the deadline error surfaces while a response is being proxied), consistent with the silent hang. This is an inference, the strongest candidate, and not a confirmed cause; the direct 60 s app result and a proxy run are needed to confirm or reject it. Alternatives not excluded: Node/Next behaviour of the app itself at 60 s for a stalled body (root's direct test decides), or Caddy internals around the total cap.

Change: `deploy/Caddyfile` sets `read_body_idle` to the same derived variable as `read_body`, so neither Caddy timer can fire before the app's deadline (cap = app + 2 s). `tests/proxyConfig.test.ts` asserts both lines exist and use that variable (comments stripped). Docs table and a "60 s probe failure" paragraph in `docs/DEPLOYMENT.md` state the status plainly. Security: no new exposure beyond the total cap already granted; a stalled connection can now live up to the cap instead of being dropped at 1 m, which for the 20 s default changes nothing.

Root's direct-app discrimination (reported, not re-run by me): compiled app with `STYLE_BODY_READ_TIMEOUT_MS=60000`, fresh synthetic data, a stalled incomplete auth body (one byte, then nothing) returned the original JSON 408 at 60.327 s, exit 0. So the app is not the cause of the 70 s silence; the proxy is. That is consistent with the `read_body_idle` explanation but does not by itself prove it (the idle timer is still an inference, not observed). The corrected Caddyfile result at 60/62 is pending from root; review of this revision stays pending on it.

**Final 60/62 result (root, local TLS loopback, internal untrusted certificate, exit 0; reported, not re-run by me):** direct and proxied 401 body, content type and private `Cache-Control` identical, proxy adds `Connection: close`; health 200 twice, ALPN `http/1.1`, second request reused the socket; counters 404; stalled incomplete body: original JSON 408 at 60.326 s, socket closed at 60.330 s before client cleanup; 1-byte/s trickle: JSON 408 at 60.327 s, closed 60.328 s. This resolves the reproduced 70 s silence for that setting and supports the `read_body_idle` explanation (the failure appeared with the default 1 m idle timer and vanished when it was set to the cap), without showing Caddy's internals. Root will rerun the 20 s default and the test file.

Remaining bounds: 120 s (cap 122 s) not tested live; no Docker or Linux, so the Compose start commands, `$$` escaping and the `caddy:2` shell are still unexercised; the case where a Caddy body timer fires before the app answers (hung app) is untested and the earlier silent-hang observation suggests it may leave the client waiting; one run per setting; Windows loopback only; no public certificate; HSTS one-year value; no per-client connection or rate limit; HTTP/2 off, not fixed; phones, load and repetition untested.

Final scoped judgment (config under review: HTTP/1.1 only, `read_header` 10 s, `read_body` and `read_body_idle` = app deadline + 2 s derived from one validated project variable, 4xx/5xx close with a single `copy_response`, counter 404, unchanged security headers and 10 MB body cap, no secrets in the proxy, app fails closed on a leftover `.env.production` value). In the measured local scenarios (20 s earlier build, 60 s) it ends a stalled or trickled auth upload with the application's own JSON 408 and a closed socket at the deadline, and it removes the manual pairing and the duplicate-header defect. It does NOT show production safety: residual availability risk from many concurrent slow uploads (each holds a connection up to the cap), the untested hung-app backstop, and the unexercised Docker, certificate and Linux path are all open. Not production ready, and no launch claim.

Open and important: what Caddy does when its own body timer DOES fire. If it also leaves the client hanging, the backstop is not a backstop for requests the app fails to answer (an app that stops responding, or a route that does not enforce its deadline). Root should force it (app 60 s, proxy cap and idle 10 s) and record reply, close time and whether the connection stays open; if it hangs, consider a `Connection: close`-style response for that path, a `read_header`/`idle` interplay check, or an external limit. Also run the 60 s and 120 s stalled and trickle probes after this change, and the 20/22 default again.

### Threat/release review of this change
Helps: removes the silent 22 s cap on a raised app limit; the app and proxy cannot disagree under Compose; invalid values fail loudly instead of falling back differently in two places; the proxy still receives no secret; the upload-counter 404, security headers, h1-only, header timeouts, close-on-error and the single `copy_response` route are untouched.

Residual risks and gaps:
1. **Not run in the real stack.** Compose `$$` escaping, `${...:-}` with the `.env` file, the `sh` in `caddy:2`, and Caddy loading the derived value are unverified. `docker compose config` must show the commands correctly un-doubled.
2. **Recreate required.** Changing `.env` and running a bare `docker compose restart` does not re-read it; `up -d` is needed. A stale proxy with a new app (or the reverse) is the old hazard; `up -d` recreates both because their config changed, but nothing checks it at runtime. A cheap check (`docker compose exec proxy printenv STYLE_BODY_READ_TIMEOUT_MS` against the app's) is in the guide's spirit but is a manual step.
3. **Migration guard is indirect and has a blind spot.** It detects the leftover through the worker, so it only protects when the worker starts; a `.env.production` line with an empty value is not detected and is harmless. A different name or a value passed another way is not covered. The mailer would also see the leftover but has no guard by design.
4. **Stricter than the app.** Under Compose an operator who had set a value the app tolerated (`" 20000"`, `2e4`) now gets a failed start, intentionally.
5. **Larger values widen exposure.** Up to 122 s per stalled upload per connection, still no per-client connection or rate limit, no per-IP limit on slow bodies at the proxy beyond that. This is the main remaining denial-of-service surface of the transport change and is unchanged by this build.
6. **Total-time cap semantics unchanged:** slow mobile uplinks above the stated sizes are refused (3 MB wardrobe needs about 1.1 Mbit/s at 22 s).
7. Carried gates (none closed): corrected Caddyfile after the duplicate-header fix re-measured (headers once, 408 timing, close before cleanup), Docker/Linux, public certificate and ACME, HSTS one-year value on first deployment, HTTP/2 off not fixed, real phones, load, repetition.
