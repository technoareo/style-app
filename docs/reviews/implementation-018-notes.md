Written for: root and the next independent reviewer.

## Build 018: reliable single-item photo path, attributes with uncertainty, and a working `VISION_MODEL`

Not committed or pushed. Not launch ready. The automated tests use a scripted mock of Ollama or a mocked HTTP answer. The only real-model evidence is the owner's handful of development runs in `docs/verification/REAL_VISION_018_ROOT.md` (4B on three photos, 2B on one, 4B again after the schema repair): samples, not a benchmark. Real-photo recognition quality, the confidence scores, and the season/occasion suggestions are **unmeasured**; they need an installed model and a set of evaluation photos whose owners consented. This note does not claim accuracy.

### What changed
- **One garment per photo is the production path.** `ANALYSIS_MODE = "single"` (`src/domain/analysis.ts`). `analyzePhoto(buffer, signal, { mode })` defaults to it; `mode: "multi"` keeps the build 016 behaviour (six items, crowded warning) unchanged and is not used in production. Crowded or multi-item photos are deferred, not solved.
  - New request: `SINGLE_ITEM_PROMPT`, `singleVisionOutputSchema` (`maxItems: 1`, every attribute required, material restricted to an enum of visible textures plus empty, fit/seasons/occasions/uncertain as enums), `num_predict` 600.
  - Attributes: category, colour, pattern, optional sleeve/neckline/closure/length (as before), plus `material`, `fit`, `seasons`, `occasions`, `uncertain` and the existing four-step `confidence`.
  - `refineSingleItem` (pure, runs before schema parsing) enforces the vocabularies: a material survives only if it is in `VISIBLE_MATERIALS` (denim, knit, leather, suede, corduroy, fleece, satin, lace, sheer, canvas, mesh); a fibre such as cotton/wool/silk is dropped and `material` is added to `uncertain`; unknown fit becomes `unknown`; seasons/occasions are filtered, de-duplicated and capped; confidence 0.25 or category `Unsorted` flags `category`. It adds nothing else. Brand and size are still forced to `""`; warmth is never inferred.
  - If the model lists several items: two shoes become one pair item (union box, "left"/"right" stripped from the name) when every item is Shoes with a usable box; otherwise only the most prominent (largest box) is kept and `MULTIPLE_ITEMS_WARNING` is shown.
- **Manual correction preserved and extended.** New shared `src/components/ItemAttributes.tsx` (material text with datalist, fit select with "Not sure", season and occasion checkboxes, "please check" hints) is used in the upload review card and in `ItemEditor`. The review shows "The AI was unsure about: …" and a plain-language confidence line. Saving still requires "Details checked". `uncertain` is a review aid and is dropped on save and by the wardrobe schema; material, fit, seasons and occasions are saved. Existing strings the browser tests rely on ("Review N detected items", "Add N items to my wardrobe") are unchanged. Upload copy now asks for one item per photo and states that fibre cannot be seen.
- **Persistence/validation.** `Garment` and `backupSchema` accept the four new optional fields with enum/length bounds; older items and older stored job results still parse. Session-storage review restore validates the new fields.
- **`VISION_MODEL` is honoured.** `configuredVisionModel()` (`src/server/vision.ts`): unset/blank gives `DEFAULT_VISION_MODEL` (`qwen3-vl:4b-instruct`); a value must match an Ollama reference shape (ASCII letters, digits, `.` `_` `-`, optional `/` parts and one `:tag`, at most 100 characters) after trimming. A **malformed value is not replaced by the default**: `analyzePhoto` throws a refundable `unavailable` `VisionError` without calling Ollama, `isModelAvailable()` returns false, and one fixed log line is written (the value is not echoed). The same function feeds the request body, the readiness check (an untagged name matches `<name>:latest`) and the worker, so they cannot disagree inside a process.
- **Docs.** `.env.example`, `README.md`, `docs/DEPLOYMENT.md` (VISION_MODEL semantics, pull-the-same-name, recreate `app` and `worker`, single-item section with the unverified statement).

### Independent review of the diff (launch risks)
Fixed during review:
- A model that lists the two shoes of one pair separately would have been cut to one shoe with a one-shoe crop and a misleading "several items" warning. Now merged (tested).
- First test draft failed `tsc` on `NodeJS.ProcessEnv`; `configuredVisionModel` takes a plain string record.

Open risks (none fixed, ordered by importance):
1. **No real-model evidence.** The prompt, the strict output schema (nested enums, `""` in an enum, array-of-enum, `const ""`) and the `num_predict` bound are untested against Ollama's grammar conversion and against Qwen3-VL. A schema Ollama rejects, a model that mislabels often, or latency from the larger grammar are all possible and unmeasured. Required before any claim: install the model, run consented photos (one item each, plus failure cases such as flat lays, folded clothes, patterns, mirrors, mannequins, two items), record per-attribute accuracy and the confidence calibration, and time it on the target CPU.
2. **Suggestions can be saved without thought.** Seasons and occasions arrive pre-ticked; "Details checked" is a single tick for the whole card. A user can persist an AI suggestion as if it were their own. The labels say "suggested" and uncertain attributes are called out, but a stricter design (not pre-ticking, or per-field confirmation) is a product decision not made here.
3. **Season/occasion/fit are inferences from a cut, not facts**, and are stored indistinguishably from user-entered values. Nothing consumes them yet (the outfit engine ignores them), so no behaviour depends on them today.
4. **`VISION_MODEL` consistency across processes is by deployment, not code.** Under Compose both `app` and `worker` read `.env.production`; locally the standalone worker loads no `.env` file, so a value only in `.env.local` can make readiness and the worker name different models (documented in `.env.example` and the README). Changing the value requires recreating `app` and `worker`; there is no check that the two agree.
5. **Prompt/schema are written for Qwen3-VL instruct.** Other models may ignore the schema or `think: false`; the parser is strict (fail closed to `unverified`/`unavailable`), but quality and cost are unknown. Only the Qwen3-VL 4B (default) and 2B have been run, a few times (see the evidence note); other models never.
6. **Bundle/exposure:** `SINGLE_ITEM_PROMPT` and the schemas live in `src/domain/analysis.ts`, which the client already imports (as it did `VISION_PROMPT`), so the prompt text ships to browsers. No secret is in it; it is a size and tidiness cost.
7. **Multi-item path** remains in the source, tested and unused; it can rot. The single path's "most prominent by box area" choice can pick a large background garment over the item the user meant.
8. **Refund/charge semantics unchanged:** a malformed `VISION_MODEL` gives a refundable failure per attempt, so a misconfiguration burns the per-day attempts counter before anyone notices; the log line and the readiness `false` are the only signals (no alert exists).
9. Account isolation, quotas, queue, deadlines, photo storage and deletion code were not touched. The new fields add a few hundred bytes per stored item; the 3 MB wardrobe bound is unchanged.

### Not done / deferred
Multi-item segmentation and crowded wardrobe photos (deferred by decision); real-model evaluation and a consented photo set; per-field confidence from the model beyond the four-step score; using seasons/occasions/fit in outfit building; a consistency check for `VISION_MODEL` between `app` and `worker`; `npm run build` and the Docker path.

## Revision 2: follow-up from the separate review and the real-photo runs

Written and tested in the same session; nothing committed or pushed. Real-model evidence quoted here is the owner's, not re-run by me.

### Fixed
- **P1: the single-item schema could never report a second item.** `singleVisionOutputSchema` allowed `maxItems: 1`, so with real Ollama the several-items warning and prominent-item selection were unreachable. It now allows `MAX_SINGLE_CANDIDATES = 3` (prompt: most prominent first, others only if clearly separate; one entry whose box covers both shoes for a pair); `num_predict` 900. Still exactly one item is presented or saved.
- **Unsafe shoe auto-merge removed.** `evidencedShoePair` replaces `mergedShoePair`: exactly two Shoes entries, names "Left X"/"Right X" with an identical rest, same colour and pattern, area ratio within 2x, gap under 12% of the frame; then the union crop plus `SHOE_PAIR_WARNING` (check the crop). Anything else (sneaker+boot, different colours, far apart, unequal size, two lefts, no sides, three shoes) keeps the most prominent item with the several-items warning (tested, 8 negative cases).
- **Real-photo shoe finding (4B, CC0 handmade shoes, 132 s):** one shoe named, crop on one shoe. A single answer cannot show which was meant, so every Shoes item (including after a category change) shows a crop-check note in the review; nothing claims the pair was captured.
- **Self-confidence (2B, shirt, 75 s, score 1 beside doubts about colour, pattern, material, fit):** `refineSingleItem` caps the score at 0.5 whenever the model also lists doubts (a fibre claim counts), never raises a score, leaves a doubt-free score alone. The UI never shows a "good/high" label; only 0.25 and 0.5 produce a note in the AI's own words, with "its scores are unverified". Persisted `confidence` is the capped value.
- **Local launch:** `src/server/localEnv.ts` + `localEnvAuto.ts`, imported first by `scripts/analysis-worker.ts`, load `.env.local` then `.env` (process env wins; nothing is read when `STYLE_PUBLIC_DEPLOYMENT=true`). A manual run from a temp directory with `.env.local` containing `VISION_MODEL=llava:7b` printed `{"ok":true,"name":"llava:7b"}` from `configuredVisionModel()` in a plain Node process. Next reads the same files for the web readiness check. The mail worker was not changed.
- **Seasons/occasions no longer pre-checked.** Drafts start with none; the AI's guess is a separate "AI suggests: ..." line with "Use these seasons/occasions"; the suggestion fields are review aids, restored from session storage after validation and dropped on save.
- **Wording:** "Review 1 detected item" / "Add 1 item to my wardrobe" (plural unchanged; the three existing e2e specs were updated to the new singular text); uncertainty reads "The AI was unsure about: category, color and material. Please check them." / "…fit. Please check it."
- **Upgrade with queued jobs:** new column `analysis_jobs.analysis_mode` (migration `018-analysis-mode`, additive, idempotent, part of the already-applied check). New jobs record `single`; a row with NULL (queued by an earlier build) runs `multi` with its original prompt and result shape. No drain needed (tested with the real queue and a mock Ollama: new job gets one item plus warning with a `maxItems 3` request, a NULL row gets both items with a `maxItems 6` request; migration idempotent on a database rewound to the old shape).
- **Provenance:** every new automated test uses generated images (sharp); none uses `tests/fixtures/public-*.jpg`. The existing e2e specs and `scripts/verify-*` still use the copyrighted public fixtures (see `tests/fixtures/SOURCES.md`); replacing them is not done and stays a launch gate.

## Build 019: repairs after independent review (config, source, tests; docs reconciled)

Not committed or pushed. Not launch ready. Items fixed, each with a test:

1. **One box rule.** `usableBox` (analysis.ts): four finite numbers, a coordinate up to 20/1000 outside the frame is clamped, anything further out is unusable, each side at least 30/1000 after clamping. The same function chooses the item (`mostProminentIndex`), validates the shoe pair (`evidencedShoePair`) and builds the final crop (`vision.ts`). Defect fixed: a candidate could win on a positive but unusable area (for example a 20-wide sliver or a far out-of-range outline) and then be shown as a full frame while another candidate had a good box; invariant tested over 49 pairs of box shapes. If every box is unusable: first listed, full frame, honest notice. Selection rule documented: largest usable box, unusable counts as 0, ties to the first listed; the prompt now asks for the item that fills most of the picture first without promising that order is used.
2. **Warnings preserved.** The crop notice, pair notice, several-items notice and crowded notice are appended to the (cleaned) model warning; the crop notice used to overwrite a genuine warning such as "blurry".
3. **Local launch parity.** `@next/env` is now a direct dependency (package.json and lock root). The worker follows NODE_ENV; `scripts/start-local.ps1` sets `NODE_ENV=production` before starting it. Finding while testing: `npm run start` runs the standalone `server.js`, whose template does `process.chdir(__dirname)` (read from `node_modules/next/dist/build/utils.js`), so the compiled web process would not read repo-root `.env*` while the worker did; `scripts/start-server.ts` now loads them (production mode, after the public-host check, before the spawn). Not verified by a build or a launch in this session.
4. **Docs reconciled** with `docs/verification/REAL_VISION_018_ROOT.md`: the real-model evidence is a handful of development samples (4B: shirt, hoodie, CC0 shoes, shirt again after the schema repair; 2B: shirt), not a benchmark; the `multi` rollback is stated to restore earlier code, not a validated crowded-photo mode; crowded photos remain unvalidated.

Earlier build 019 items (reviewer-confirmed): rollback switch `STYLE_ANALYSIS_MODE` with stored per-job mode, warning-boilerplate filter, `@next/env` loader, capacity paragraph.

### Build 019 follow-up: warning length and manual launch parity

- **P2 fixed.** An over-long model warning could exceed `analysisSchema`'s 500-character cap once the crop/pair/several/crowded notices were appended, which failed the whole analysis as `unverified`; in `analysisJobs.ts` that maps to failure kind `model`, which is not refunded, so a valid item cost the user an allowance. `composeWarning` (analysis.ts) now bounds the MODEL's text first (cut at a word boundary with an ellipsis, leaving room for the notices) and appends the fixed notices in full; the largest notice set the code can produce (crop with crowded, about 320 characters) leaves about 180 for the model. The same class of failure for item text is closed in single-item mode: `name`, `color`, `pattern`, `evidence`, `sleeve`, `neckline`, `closure` and `length` are cut to their schema caps instead of failing the analysis. Regression tests: a 3,000-character warning with crop plus several-items, crop plus shoe-pair, and (multi mode) crop plus crowded notices; `composeWarning` edge cases (exact fit, no room, no notices); over-long item fields. These were written after the fix and were not observed failing against the old code, except that the old composition has no length bound by construction.
- **P3 documented.** README now states that the compiled app needs its worker started with `NODE_ENV=production` (or `scripts/start-local.ps1`), and that shared settings belong in `.env.local`.

### Build 019 follow-up: remaining single-item schema edge cases

- **Fixed (single-item mode only; the multi-item path and its schema are untouched):** `refineSingleItem` now repairs before verification instead of letting these fail the parse: empty or missing name (kept empty; new `reviewAnalysisSchema` accepts it for the review screen, and the Add button stays disabled until the user names the item, with a "Name this item" placeholder), brand and size (always blanked first, so a long value cannot fail), non-text required fields (empty and flagged), category outside the list (Unsorted, flagged; saving is blocked until the user chooses), formality outside the list (unknown), confidence missing/non-numeric/outside 0..1 (0.25, which also flags the category). Entries that are not objects pass through unchanged, so they still fail verification as "unverified" rather than becoming a blank item.
- **Charge/refund, checked in code and by a real-queue test:** a repaired item completes and is charged once; a non-item entry fails as failure kind `model`, `refunded` stays 0 and the daily count is charged (unchanged policy: only server-side failures are refunded).
- **Tests:** unit (bare/complete items, non-items, empty names, long brand/size, out-of-vocabulary category/formality, six junk confidences, non-text fields, non-item entries rejected), real-queue charge test, and a browser test that an unnamed, Unsorted suggestion cannot be saved until named and sorted. Written alongside the fix, not observed failing against the old code.
