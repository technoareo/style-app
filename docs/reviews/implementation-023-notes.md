## What build 023 adds
A real Docker Compose + Caddy smoke test in the existing CI `docker` job. It starts `app` and `proxy` from the **shipped** `compose.yaml` and `deploy/Caddyfile`, on the image the job just built from the checkout, with no model download, no SMTP delivery, no public domain and no external account. (`caddy:2` and `node:24-bookworm-slim`, which runs the mock model, are not built from the checkout and may be pulled from a registry; only the `app` image is built.) The override's mock mount path is valid in the throw-away project folder the runner creates and copies the mock into, not from the repository root, and production services running on the same host are left alone: smoke resources are all named `style-smoke-<run id>` and use loopback ports 18080/18443. It is scoped to the supported easy single-item product; nothing about crowded photos.

## How each requirement is met
1. **Real compose substitution and startup.** `docker compose -p style-smoke-<id> --project-directory <tmp> -f compose.yaml -f compose.smoke.yaml up -d --no-build --wait app proxy`. The project `.env` carries `STYLE_DOMAIN` (and the timeout when a case needs it); `.env.production` is generated. Compose therefore does the real `${STYLE_BODY_READ_TIMEOUT_MS:-20000}` and `${STYLE_DOMAIN:-}` substitution, the real start commands run, and `--wait` waits for the app's real healthcheck. Worker and mailer are asserted not to start.
2. **Isolation; production unchanged.** The shipped files are copied byte for byte (the runner verifies the hash of each copy) into a temp folder; only the override differs. `docker compose config --format json` is taken with and without the override and every differing path must be on `ALLOWED_OVERRIDE_DIFFS`; a unit test mutates a config to show that a changed command, environment value, healthcheck, `cap_drop`, mount or an extra service is caught. TLS: site name `style-ci.localhost` is served from Caddy's own internal CA (no ACME), and the app accepts it as a public `APP_URL` (it rejects only the exact names `localhost`, `127.0.0.1`, `0.0.0.0`, `::1`; a test mirrors that rule). The client trusts only the root certificate read from the proxy container. Routing, security headers, `protocols h1`, the health route, the hidden `/api/health/uploads` and `reverse_proxy` are all the shipped Caddyfile.
3. **Timeout derivation and fail-closed behaviour in real containers.**
   - *Default 20000 and raised 30000:* the running server process's own `STYLE_BODY_READ_TIMEOUT_MS` is read from `/proc` (the container's PID 1 is the shell, which exports it after the process starts, so `compose exec printenv` would say nothing). **Which process:** the standalone server sets its own process title, so its `/proc/<pid>/cmdline` reads `next-server (v15.5.27)`, not `node server.js`; the probe (`PROC_ENV_SOURCE`) accepts a process whose first command-line token starts with `next-server (v` (the full title is `next-server (v15.5.27)`, but Linux keeps a process title only as long as the original argument block, 14 characters for `node server.js`, so the kernel may report just `next-server (v`; or, before the title is applied, exactly `<path>/node server.js`), that is not the probe itself (own PID, also given as an argument for tests) and that has the variable in its environment, and the runner requires exactly one such process. A shell that only mentions the script, another node program, similar names (`next-server-helper`, `next-server` without a version) and a second real server are covered by tests; the proxy's PID 1 `STYLE_PROXY_BODY_READ_TIMEOUT_S` must be `ceil(ms/1000)+2` (22, 32); Caddy's admin API (`/config/apps/http/servers`) must show that number as a read timeout, 10 s as the header timeout and `["h1"]`. The JSON key names are deliberately not asserted (they vary by Caddy version); the values are found by meaning and the whole timeout object is printed so the first run records the real names. A stalled upload through the proxy must get the application's own 408 after at least 90 % of the app deadline and strictly before the proxy cap, with `Connection: close` and a closed socket. Runtime: about 20 s + 30 s of probe time plus two `up --wait` cycles.
   - *Invalid values and stale placement:* seven invalid values make `docker compose run --rm --no-deps` of **both** `app` and `proxy` exit 1 with the shipped message and start nothing (no "Auth schema" line, no Caddy "serving initial configuration"). Through full `docker compose up`, an invalid project value and a stale `STYLE_BODY_READ_TIMEOUT_MS=30000` in `.env.production` each leave the app `exited` with code 1 and its message in the log, with the proxy, worker and mailer not running. An empty `STYLE_DOMAIN` stops the proxy. The shell rule and the `+ 2` arithmetic are also tested here, against the real `compose.yaml` text with a POSIX `sh`, for 21 values.
4. **Direct versus proxied.** The "direct" request is made from inside the `app` container to `127.0.0.1:3000` (so no extra port is published) and returns the raw header list. For 401, 403, 404, 413 and 503 + `Retry-After: 5` the status and body must be equal and `compareHeaders` must report no problem: every app header arrives with identical value(s) (catches the earlier duplicated-`Cache-Control` defect), the proxy adds only `Server`, `Via` and the five Caddyfile headers (exact values from the Caddyfile, a test keeps them equal), `Vary` may gain `Accept-Encoding`, and the error says `Connection: close`. The 503 is produced deterministically: a `node -e` program inside the app container takes `BEGIN IMMEDIATE` on `/data/app.db` and holds it for 8 s while a sign-up is sent directly and through the proxy; with `STYLE_AUTH_LOCK_MS=200` the app refuses it as its own retryable busy 503. Successful health: 200 twice on one kept-alive connection (`reusedSocket`), `Cache-Control: no-store`, no `Alt-Svc`, ALPN `http/1.1` when `h2` is offered, plain HTTP redirects to HTTPS. Counters: 404 for the four spellings the Caddyfile matches, and three variants (upper case, percent-encoded, double slash) must not return the counters body; the app itself answers the route with 200 directly.
5. **Deterministic scripts and tests; cleanup and logs.** See Files. The passing and failing paths of `runSmoke` run against a fake docker that tracks resources: project folder (holding the secret) removed, `down -v` issued after a failure, name sweeps for containers, volumes and networks, a leftover fails the run, a secret in any argument/output/log fails it, errors and logs are redacted, and the redacted logs are written to `SMOKE_LOG_DIR`. `compose config` output (which inlines `.env.production`) is excluded from the leak scan on purpose.
6. **No real model, SMTP, certificate authority or account.** The model is the CI mock; the mailer is never started; `SMTP_URL` is `smtp://127.0.0.1:2525`, which nothing connects to; Caddy's internal CA only.

### Second and third review, B1 (probe could never match in the real container)
The first probe matched only a command line of exactly `node server.js`. In the real Next 15.5.27 standalone container `start-server.js` sets `process.title` to `next-server (v15.5.27)`, so it would have found no process and failed the first Docker run before any meaningful check. A first fix required the complete `next-server (v<semver>)` with its closing parenthesis; the third review pointed out that the title can be truncated to `next-server (v` (14 characters, the length of `node server.js`), which that rule would have rejected. `PROC_ENV_SOURCE` now requires the prefix `next-server (v` at the start of the first token, which accepts the full and the truncated form and still rejects bare `next-server`, `next-server ` (space only), `next-server-helper (v1.0.0)`, `next-server (x1)` and a title not at the start. ### CI run 41086578325: wardrobe route test failed before Docker (fixed in the test only)
**Failure (reported from GitHub Actions, run 41086578325).** `npm test` in the `build` job, before any Docker step: `tests/wardrobeRoutes015.test.ts:239`, "PUT validation precedes the wardrobe transaction: after admission, invalid documents are refused while the gate is held; a valid one queues for the gate and then commits", `Error: condition not reached in time` at line 93 (`until`), called from `putAfterAdmission` (line 132) and the test (line 252). Suite totals reported: 469 tests, 466 pass, 1 fail, 2 skipped. The same test failed once in my own full runs earlier (it passed alone each time), so this is the second sighting.

**Diagnosis.** The build 015 file is unchanged by build 023 (no application code or wardrobe test was touched by it). The failing line waited for "admission is finished" (the change-quota row moved after the session lookup and a write through the process write gate) with a fixed 5 s polling deadline. There is no hook to signal admission, so it was polled; on a two-CPU runner that executes test files in parallel, 5 s can be exceeded by a healthy request. Two more waits in the same helper had the same weakness: a 3 s window for "answered while the gate was held" and a 300 ms window followed by an exact "one waiter" count (the waiter may simply not have reached the gate yet). I did not find evidence of a product race: nothing in the failure shows the handler took a wrong path, and the test passed in 12 of 12 isolated runs afterwards. That is an inference from the failure text and from repeated passes; I could not reproduce the CI failure itself, and I did not stress the machine to try (an artificial CPU-load run was started and cancelled at the owner's request).

**Fix (test synchronisation only, `tests/wardrobeRoutes015.test.ts`; no application code, no assertion removed or weakened).**
- `until` now takes a generous backstop (`EVENT_BOUND_MS` = 60 s, only a hang guard) and an `abort` callback, so a wait ends immediately, with the real reason, if the PUT answered (status named) instead of reaching the expected state.
- `putAfterAdmission(s, text, "answers" | "queues")` replaces the `holdMs` numbers. "answers" (invalid documents): waits until the handler answers, and stops at once if a waiter appears at the write gate, because that means validation did not come first; the assertions `answeredWhileHeld === true` and `queued === 0` are unchanged. "queues" (valid document): waits until the gate has a waiter, then checks that with the gate held and a waiter queued it has not answered (a 200 ms settle window is a sanity check, not the synchronisation), and the assertions `answeredWhileHeld === false`, `queued === 1`, status 200, `{ revision: 1 }` and one stored row are unchanged.
- **Correction (independent review of this fix).** An earlier version of this note said the other short windows in that file could not fail on a slow machine. That was wrong. The admission test waited 300 ms and then asserted `writeGateQueueLength() === 1`, which fails if a healthy PUT has not reached the gate yet, and several 3 s "answered without the gate" windows were latency bounds. All were fixed in a second pass (below).

**Second pass (review findings, same file, test code only).**
1. *Same-class timing dependence, all inspected and fixed:*
   - Admission test ("an authenticated PUT waits in ADMISSION"): now waits for the event (`writeGateQueueLength() >= 1`, aborting at once with the real reason if the PUT answered), then checks it has not answered and the queue is exactly 1 and the quota still 0. The 300 ms window is only a sanity check after the event.
   - Refusals of no session / wrong origin / wrong account, and the GET under a held gate plus a foreign SQLite lock: the 3 s windows are replaced by `answerWhileGateHeld`, which returns the moment the handler answers, ends at once if a waiter appears at the gate (the defect: queued instead of answering), and otherwise has only a 60 s hang backstop.
   - GET with an expired photo and a stalled cleanup: this one is queued at the gate on purpose for the product's own bounded cleanup wait (`RECLAIM_ACQUIRE_MS`, 2 s), so it cannot use the waiter signal. Its two bounds were `2 s + 3 s` to answer and `< 2 s + 2.5 s` elapsed; both are now `RECLAIM_ACQUIRE_MS * 5` (10 s), a reasoned latency bound that still fails a handler that hangs waiting for the gate. The lower bound (`>= RECLAIM_ACQUIRE_MS - 300`) is unchanged. This one remains a timer-based bound by nature; it is looser, not event-based.
2. *Early answer / cleanup:* `putAfterAdmission` now checks, after the admission wait and again after acquiring the gate, whether the PUT already answered; if so it fails with a clear message (`the PUT answered <status> before the test delivered its body`) instead of sending a body to a finished request. `controlledBody().send` is idempotent and swallows the error a finished or cancelled stream throws; a new `abandon()` errors a body that will never be delivered, and every failure path in the helper calls it, so a waiting handler cannot hang; the gate release stays in `finally` (idempotent).
3. *Strictness kept:* the invalid-document path still stops at once when a waiter appears at the gate; every original assertion (`answeredWhileHeld`, `queued`, statuses, `{ revision: 1 }`, row counts, quota values) is unchanged.
A new test in the same file covers the helpers themselves (the defect path ends well before the backstop; the answered path; `send`/`abandon` idempotence and no throw after a finished body). The file now has 7 tests.

## Risks and limits (honest list)
1. **Never run.** Every Docker-dependent step is untested: `!override` merging, `up --wait` behaviour with the mock model, `compose run --no-deps` exit codes and stderr passthrough, `ps --format json` shapes (both are parsed), Caddy's admin endpoint being reachable with `wget` in `caddy:2`, the internal CA path `/data/caddy/pki/authorities/local/root.crt` and how soon it exists (polled for 90 s), whether `Via` and `Server` are the only headers Caddy adds, and the exact timing windows. The checks are strict by design; a first-run failure is likely to be a wrong assumption in the test, not a product defect, and the logs and the printed Caddy timeout object are there to tell the two apart. Do not weaken a check without reading what the real run printed.
2. **`.localhost` TLS** is Caddy's own CA, not a public certificate. Public ACME, DNS, certificate renewal and a trusted chain are untested.
3. **Override differences are real differences.** `restart: "no"`, loopback high ports, the CI image and the mock model are not what production runs. Restart behaviour and ports 80/443 are not exercised.
4. **The 503 test depends on the app's busy path:** a sign-up under a held write lock must end in `busyResponse()`. If Better Auth ever stops flagging the contention, the test fails loudly (status or `code: "busy"`), which would itself be a product finding.
5. **Timing windows** (`>= 90 %` of the app deadline, `< cap − 100 ms`) assume a quiet CI runner. A heavily loaded runner could make the 20 s case flaky; widen the lower bound, not the upper one.
6. **Not covered:** HTTP/2 (off by design), a real browser, slow or mobile links, concurrent stalled connections, the 3 MB wardrobe save, 120000 ms, worker and mailer containers, SMTP, any model, large uploads through Caddy's 10 MB `max_size` (the 413 case exercises the application's 32 KiB auth limit, not Caddy's).
7. **Found while reading, not changed:** the `app` command in `compose.yaml` ends `&& node server.js` without `exec`, so `docker compose stop` signals a shell and waits out the stop timeout (the mailer already avoids this). Production compose is out of scope for this build; this is recorded in `docs/DEPLOYMENT.md` and left for a decision.
8. The first CI job takes longer: roughly two minutes of `up --wait` cycles plus about 50 s of stalled-upload probes plus the failure matrix; the step ceiling is 15 minutes.
