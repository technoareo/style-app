# Implementation 026: rights-cleared photo intake and gold-label workflow

Status: implemented and tested with synthetic photos only. **Uncommitted** (no commit, no push). The app is **not launch-ready**: this build collects and freezes a benchmark; it measures nothing, and no real photo, label or model result exists in the repository. Recognition stays unmeasured until a representative, rights-cleared real-photo benchmark has been acquired, labelled by people, frozen, run with `single-run-qwen` and has passed an approved policy.

## Scope

A production-quality, local-only intake and labelling workflow for the supported **easy single-item** photo workflow, integrated with the Build 024 manifest/gold/receipt/integrity code and the Build 025 runner and scorer. Crowded and multi-item photos are out of scope. Research found DeepFashion non-commercial only, ModaNet CC BY-NC and Fashionpedia not owning its image copyrights, so **no public dataset is downloaded or depended on**; DeepFashion, ModaNet and Fashionpedia are refused by name in rights evidence. Only operator-supplied JPEG, PNG and WebP files are imported.

New code (all under `scripts/vision-evaluation/single-item/`): `fsx.ts` (safe reads, exclusive writes, rollback), `intake.ts` (rights and capture schemas, image examination, signatures, workspace, import, seal), `review.ts` (reviews, independence, agreement, adjudication, gold), `sampling.ts` (coverage spec, deterministic plan, freeze), `readiness.ts` (privacy-safe report), `cli-intake.ts` (commands), plus additive edits to `image.ts` (WebP), `vocab.ts`, `manifest.ts`, `templates.ts`, `gold.ts` (exports `MODEL_LIKE`), `integrity.ts` (message text only), `run.ts` (routing) and `.gitignore`. Tests: `tests/singleItemIntake026.test.ts`.

## Decisions

1. **One workspace, private by construction.** `single-intake-init` creates `pool/` (exact image bytes), `records/` (one strict JSON intake record per photo, written last, so it is the commit point), `reviews/`, `adjudications/` and later `seal.json`. A workspace is never reused. Everything in it is git-ignored (`benchmark-intake/`, releases, reviewer notes, `*.rights.json`, `*.release.*`).
2. **Rights evidence is per photo and closed.** `self-captured`, `contributor-consent` or `open-license`; holder, acquisition date, `evaluationPermission: true`, a recorded `redistributionAllowed`, an individual verification by a pseudonymous operator, a consent reference for contributors, and for open licences a collection, https page and file URLs, an allow-listed licence (unchanged Build 024 list) and attribution. Unknown, public-web, scraped, other, NC/ND licences, http URLs and public fashion datasets are refused.
3. **Manifest change (additive, strict).** Build 024 rights required URLs and a licence. Two new collections, `self-captured` and `contributor-consent`, require `sourcePageUrl`, `originalUrl` and `license` to be **null** and `creator` to be a pseudonymous `rh-<12 hex>` reference (derived from the holder with a per-workspace secret salt), never a name. The three older collections keep their rules exactly. Types became nullable accordingly; the leakage check already skipped null keys.
4. **People.** A photo with a person needs a model release (reference, date, `coversEvaluation: true`); a `worn` scene must declare a person; a release without a person is refused. Reviewers flag `personVisible`, and a person they see that the import did not declare excludes the photo.
5. **Image safety.** Content is sniffed (the name does not decide) and executables, scripts, archives, PDFs and GIFs are named and refused; the extension must match; bytes after the end of the image (JPEG EOI, PNG IEND, WebP RIFF length) are refused; truncated, undecodable, animated, tiny (<224 px) and >80 MP images are refused; header and decoded sizes must agree. WebP dimensions and EXIF orientation are measured by a new header reader in `image.ts` (additive; JPEG/PNG behaviour unchanged).
6. **Windows-safe file handling.** Source names must be bare: no separators, `..`, drive letters, `:streams`, control characters, trailing dot/space, or device names (CON, NUL, COM1 ...); duplicates are compared case-insensitively. `lstat` refuses symbolic links and junctions (file and directory), non-regular files and hard-linked files; the real path (`realpath.native`) must stay inside the source directory; the read is bound to the opened handle's identity (strengthened in Build 027, see implementation-027-notes.md; the original size-and-mtime check was found insufficient in review). Output uses exclusive create only (open `wx`, write, fsync, close) with rollback of what that call created: no rename, no hard link, no copy-by-name, no recursive delete (a source guard test enforces it). Refusal messages never contain the operator's file name or the holder's name.
7. **Duplicates.** Exact bytes anywhere in the pool are refused. A 64-bit perceptual hash (EXIF-oriented, with its mirror image) plus a 3x3 colour grid finds re-encodes, resizes and mirrors; such a pair must **declare the same shoot and garment** or the import is refused, and then the pair is linked and forced into one split. After the seal, anything near-identical to, or sharing a shoot or garment with, a held-out photo is refused.
8. **Labels.** Review files are strict (exact image hash, start before finish, not before import, not in the future, closed vocabularies, `unknown` allowed, pseudonymous `rv-` ids, no model-like ids or tools, `modelAssisted: false`). Held-out needs two reviews; agreement means equal presence/outcome/category/colour/pattern/fit/material/`personVisible` and box IoU >= 0.75 (final box is the mean, seasons/occasions the intersection). Disagreements need a third person (an adjudicator who is neither reviewer, in another session, finishing after both, naming the two reviewers, adjudicating only disagreements). `unsure`, `unknown` category/colour/pattern, a human decision that contradicts the import declaration, and undeclared people are excluded with a reason, never defaulted. Output is a normal `single-item-gold` file (`double_human_adjudicated`, annotators listed), validated by the unchanged validator. A single review is allowed only with `--development-single-review` and never reaches the held-out split. Copy checks: same reviewer or session, identical content, identical full-precision boxes (>10 % of jointly reviewed items), identical notes (>=2), identical timestamps (>10 %).
9. **Sampling.** Coverage spec = totals plus minimums per category (all six required), colour, pattern, background, lighting, camera, item size and wearable type; it must be at least as strict as the launch policy and needs a seed a person wrote down. Groups (same shoot, same garment, near-duplicates) are union-found over all imported photos. Selection is greedy by gain with ties broken by `sha256(seed:group)`: the same inputs always give the same plan, independent of load order. Item size comes from the gold box area (<0.12 small, <0.45 medium, else large); wearable type from the scene. The plan lists every cell as `have/need/deficit`.
10. **Freeze.** `single-intake-freeze` recomputes the plan and refuses a stale or edited one, any deficit, a single-reviewed held-out photo, an existing output directory, an already sealed workspace, changed pool bytes, or any failure of the **unchanged** `validateSingleManifest`, `validateGoldFile`, `validateFreezeReceipt` and `integrityProblems`. It writes images (per-split folders), manifests, gold, receipts (receipts last) and then `seal.json`, rolling back everything it created on failure. Receipts name the sha256 of the exact manifest bytes, as `single-freeze` does.
11. **Report.** `single-intake-report` writes counts and generic blockers and a READY / NOT READY verdict for collection and freeze only. Tests assert it contains no holder, reviewer, operator, URL, file name, release reference or image id, and no accuracy figure.

## Manual steps (nothing here can do them)

Obtain or capture the photos and keep the proof (consent forms, signed releases, licence pages) somewhere private and separate. Fill the intake batch truthfully (`single-template --kind intake-batch`). Keep the pseudonym-to-person lists outside the workspace. Have genuinely different people review without conferring, and a third person adjudicate. Choose the coverage minimums and the seed. Run `single-sample`, collect more photos until it reports no deficits, then freeze. Approve the launch policy, run `single-run-qwen`, `single-adapt-qwen --run-dir` and `single-score` as in implementation 025.

## Limits, stated plainly

- Rights evidence is attestation. The tool does not fetch pages, read releases or verify that a licence is what it is said to be.
- It cannot prove two pseudonyms are two people or that reviewers did not talk; copy detection is heuristic.
- There is no face or person detection. A person that nobody declared and no reviewer flagged would pass.
- Near-duplicate detection misses heavy crops, edits and different shots of one garment; correct shoot and garment ids are the real protection and are only as honest as the operator.
- The workspace and the seal are unsigned and not tamper-proof: anyone who controls the machine can rewrite records, reviews and the seal consistently. Strict parsing and pool re-hashing catch accidents and partial edits, not a determined forger.
- Not a transaction: a crash or power loss can leave a pool file without a record (reported by the pool check) or a partial freeze directory (a freeze needs a new directory; delete the old one by hand). Rollback covers ordinary failures.
- Sealing is procedural. The tool refuses later imports of related photos and any refreeze, but the held-out files are ordinary files.
- Default coverage numbers and the item-size thresholds are the builder's proposal, not standards; the greedy selection is deterministic but not optimal and reports shortfalls rather than hiding them.
- Decoding untrusted images uses libvips through sharp (80 MP cap) on operator-supplied files; that is an attack surface the file checks reduce but do not remove.
- Tests use synthetic block-pattern images only. Symbolic-link behaviour was tested through an injected file system, plus a real junction where the OS allowed creating one. Nothing was run on the root's managed Windows sandbox, against Ollama, or with real photos.

## Results (run on the Windows 11 development machine, after the final edits)

- `npx tsc --noEmit`: clean (exit 0).
- `npm run lint` (ESLint over `src`, as configured; the new files live under `scripts/` and `tests/`, which that script does not cover): exit 0.
- Focused: `tests/singleItemIntake026.test.ts` 33/33 pass; together with `singleItemRunner025` (71), `singleItemGate024` (54), `visionEvaluation`, `visionCap016` and `deploymentScripts`: 214 tests, 214 pass, 0 fail.
- Full `npm test`: 634 tests, 629 pass, 0 fail, 0 cancelled, 5 skipped.
- Without the new file the suite is 601 tests, 596 pass, 0 fail, 5 skipped, i.e. nothing from Builds 024/025 changed. A first full run with the new file failed once more in `tests/concurrency.test.ts` ("database is locked" under load); it passes alone (7/7) and passes together with the new file, and it stopped failing after the production-scale test was made lighter: that test now injects a no-fsync file system through the tool's own `FsOps` seam (fsync stays in the tool; it costs about 15 ms per file on Windows) and the file caps sharp at one thread. The flake is a timing sensitivity of that test under CPU load, not something this build changes.
- The production-scale command-line test imports 400 synthetic photos (330 in-scope, 70 rejection) with all three rights types and people with releases, takes two reviews, samples against the default coverage spec and default policy minimums (300 held-out including >= 240 in-scope and >= 60 rejection, >= 60 development), freezes, seals, re-runs the unchanged `integrityProblems` on the result, refuses a second freeze and writes the report.

Not run: Ollama or any model, real photos, the root's managed Windows sandbox, a non-Windows OS.
