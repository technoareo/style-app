## Research basis (not legal advice)

The need for privacy information at the point of collection comes from regulator guidance that root verified at the primary sources: the UK ICO's "What privacy information should we provide?" (https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/the-right-to-be-informed/what-privacy-information-should-we-provide/), which lists the controller's name and contact details, the purposes, the lawful basis, recipients, retention, individual rights and how to complain; and the California Attorney General's CCPA page (https://www.oag.ca.gov/privacy/ccpa), under which a notice at collection must be given at or before collection and link to the privacy policy. A general research assistant had also recommended privacy, terms and support disclosure at collection points. **This is not legal advice and this repository drafts no legal document.** Which law applies to a given operator, and what the documents must say, is an external legal task.

## What this build does (an engineering guard, not a policy)

1. **Configuration (`src/server/launchInfo.ts`, server-only).** Exactly three operator destinations, read from the environment at call time: `STYLE_PRIVACY_URL`, `STYLE_TERMS_URL`, `STYLE_SUPPORT_URL`. Strict, fail-closed parsing: trimmed; printable ASCII only (no space, control, bidi or non-ASCII character; international host names in punycode); no `#` fragment; no credentials (including an empty `@`); no backslash; at most 2048 characters; already in canonical `new URL` form. In a public deployment (`STYLE_PUBLIC_DEPLOYMENT=true`, exact word) privacy and terms must be absolute `https:` URLs on a public host with no explicit port; support may also be a single plain `mailto:` address (no query, list, display name or percent-encoding) on a public host. The public-host rule is deliberately stricter than the existing `APP_URL` check (which only refuses a few loopback names): at least one dot, ordinary DNS labels, a letters-only or punycode final label, no trailing dot, no IP literal of any form, and not `localhost` or any name ending `.localhost`, `.local`, `.internal`, `.localdomain`, `.lan`, `.home.arpa`, `.test`, `.invalid` or `.example`. It proves nothing about ownership or resolution. A bad value returns the fixed `{ ok: false }`: it is never echoed, logged or placed in a message. Outside a public deployment `http` and internal hosts are accepted so links can be tried locally; every other rule still applies.
2. **Routes (`src/app/privacy|terms|support/route.ts`, `src/server/launchRoute.ts`).** Stable same-origin `GET` routes, `force-dynamic`, read at request time (no `NEXT_PUBLIC_` value, which would be fixed at build time and could not follow Compose configuration). A valid `https` destination gives `307` with `Location` set to it, `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. A valid `mailto:` support destination gives a fixed-structure `200` HTML page instead (see "Reviewer finding" below). The handlers take no argument, so nothing in the request can reach the `Location`: no open redirect. A missing or invalid value, including in local development, gives one fixed `503` page (no-store, `X-Robots-Tag: noindex, nofollow`, `<meta name="robots">`, restrictive CSP) that names only the kind of page and contains no operator identity, no legal wording and no value.
3. **Links.** One shared component, `LaunchInfoLinks`, renders plain anchors to `/privacy`, `/terms` and `/support` at the foot of the sign-in / create-account / reset card (visible in every mode) and in the signed-in footer. `PhotoPrivacyLink` puts one "How your photo is used: Privacy information" link (new tab, `noopener noreferrer`) directly after the existing photo-consent checkbox. No new checkbox, no acceptance step and no change to the consent text or logic.
4. **Readiness (fail closed).** `assertLaunchInfoConfigured()` runs inside the memoised auth build (`src/server/auth.ts`) next to the existing public-mode checks. With `STYLE_PUBLIC_DEPLOYMENT=true`, if any destination is missing or invalid it throws a fixed message naming only the variable names. At container start `init-auth` therefore stops the `app` container before the server starts (the same behaviour as the existing missing-SMTP check), and wherever the server is running `/api/health` returns its unchanged fixed public body `{"ready":false}` with 503 and no reason. Local development and every existing non-public test are unaffected.
5. **Wiring and docs.** The variables are set in `.env.production` (the app's `env_file`), not as Compose `${...}` entries: an `environment:` entry with an empty default would silently override the file, the lesson already recorded for the body-timeout variable. `compose.yaml` gains a comment saying so; the proxy never loads that file; the worker and mailer do not read these variables (they share the file but ignore them). `.env.example`, `.env.compose.example` and `docs/DEPLOYMENT.md` document them. The CI Compose smoke test's generated `.env.production` now carries three valid public destinations on `example.com` (the app refuses `.localhost`, which the smoke site uses for `APP_URL`); the app only redirects to them, so no network access is involved. No `APP_URL`, TLS or security guard was changed.

## Tests (`tests/launchInfo032.test.ts`, new)

Parsing tables (accepted forms; rejected schemes, relative and protocol-relative values, credentials, fragments, control and hidden characters, non-canonical spellings, ports, loopback, private, numeric and IPv6 hosts, single labels, internal and reserved suffixes, mailto variants, over-long values, non-strings); local-development relaxations; hostile values never echoed in results, thrown messages or `resolveLaunchInfo`; the public/local readiness rule and the variable-names-only message; the three routes' 307 and fixed 503 (identical body whatever the bad value was, no `Location` on failure, no-store, noindex, no value in any header or body, runtime pick-up of a changed value, handlers that take no request); the links at the three collection points as plain same-origin anchors with no new consent; Compose wiring (no entry in `compose.yaml`, only the app reads `.env.production`, no worker or mailer use) and the CI smoke values accepted by the real validator; the real auth and health path in its own process (not ready without the settings, still `{"ready":false}` and silent for hostile values, ready with valid ones, with console output captured and searched for the hostile marker); and the documentation. The tests assert behaviour and observable contracts, not the implementation's internals.

## Reviewer finding: `/support` redirect to `mailto:` (fixed before commit; revalidated by root on Windows; final re-review pending)

The independent (Claude) reviewer returned READY TO COMMIT BUILD 032 but raised a production concern to fix before commit: answering `/support` with a `307` whose `Location` is a `mailto:` URI can fail in browsers, which may treat a redirect to a non-http(s) scheme as unsafe. This change addresses it narrowly:

- When the validated support destination is `mailto:`, `/support` returns a **fixed-structure `200` HTML page** with a labelled line ("To contact support, email:") and **one** plain `<a href="mailto:ADDRESS">ADDRESS</a>`. The address is the validated one and is HTML-escaped again for the href and the text (defence in depth: validation already excludes markup). The response has no `Location`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow`, `<meta name="robots">` and the restrictive CSP (`default-src 'none'; style-src 'none'; base-uri 'none'; form-action 'none'`). The page has no script, form, embed or external URL.
- `https` support destinations still return the existing `307`; `/privacy` and `/terms` are unchanged; a missing or invalid value still returns the fixed value-free `503` page.
- The live Compose smoke test now checks, both directly inside the app container and through the proxy, that `/privacy` and `/terms` answer `307` to exactly the configured destinations and that `/support` answers the `200` mailto contact page with no `Location`. The check (`launchRouteProblems`, pure) only inspects the answers: **no destination is ever requested or followed**, so it needs no network access to `example.com`. A misplaced comment in `scripts/ci-compose-smoke-plan.ts` (the env-file note had been left above the launch constants instead of above `appEnvFile`) was corrected. No existing smoke assertion was weakened.
- Tests: `tests/launchInfo032.test.ts` now asserts the mailto `200` page (status, headers, no `Location`, one link, exact structure, nothing else in the page), escaping of unusual valid addresses and defence-in-depth escaping of markup characters, that hostile or invalid support values keep the fixed `503`, that `https` support and privacy/terms are unchanged, and the smoke checker against real route answers and wrong ones. No browser-level test was added: the existing e2e architecture has no deployed support address, so the route contract test is the focused, stable check.

**Review history and status.** The Claude reviewer initially returned READY TO COMMIT BUILD 032 while identifying the mailto redirect concern; the builder fixed it **before commit**, and root then **revalidated the post-fix tree on Windows** (results under "Validation, after the mailto fix"). The earlier Windows results are kept below only as the pre-fix record. **Still pending:** a final independent re-review of the fixed build, and Linux GitHub CI after commit and push, where the new live launch-route smoke checks (`/privacy` and `/terms` 307 to the configured destinations, `/support` the 200 mailto page, both direct and through Caddy) have not yet run and are what remains to be proved.

## Remaining gates (unchanged or created by this build)

Configured links **do not make the legal documents adequate**: a link to a page is not compliance. Still external and open: **operator identity**, **jurisdiction**, **legal review** of the privacy notice and terms, and actual **monitored support** behind the support address. Also unchanged and open: **hosting**, a real **domain** with publicly trusted **TLS**, a **real SMTP** relay with delivered mail, an **off-server** backup with a restore tested on a different machine, **capacity** measured on the operator host, and a representative **rights-cleared** benchmark that passes an approved policy (recognition quality is unmeasured). The supported workflow remains easy single-item detection; crowded photos stay deferred. The product is not launch-ready.
